**判定口径**：每项要么给出「过」的证据（命令输出、截图、生成代码片段），要么明确写「退路已启用」。不允许留「大概能行」。尚未到期、按计划推迟的项标「未到期」并注明时点（本节于 2026-11-20 补此说明，因为 V8 本来就要等到第 10 周用例之后）。

### V5 sqlc jsonb — 过

```
$ go run github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1 generate
```

`sqlc.yaml` 的两条规则：

```yaml
overrides:
  - db_type: jsonb
    go_type: { import: encoding/json, type: RawMessage }
  - db_type: jsonb
    nullable: true
    go_type: { import: encoding/json, type: RawMessage }
```

- 非 nullable 的 `capability_state.value` / `state_history.value`：一条规则就够，`UpsertStateParams.Value` 与扫描字段都是 `json.RawMessage`；
- nullable 的 `command_log.target`：**必须再加 `nullable: true` 那条**。第一次生成时它是 `Target []byte`，加上后才变 `json.RawMessage`——这是一个静默失败点，漏了不会报错，只会在 handler 里炸出类型不匹配。

实测往返：

```
V5 OK: value 往返 {"on":true,"brightness":80} -> {"on": true, "brightness": 80}
```

### V6 同事务 — 过

```
V6 OK: 同一事务内两表一起回滚
V6 OK: 同一事务内两表一起提交
```

同一 `pgx.Tx` 内先 `InsertCommand` 再 `InsertHistory`；回滚后 `command_log` 与 `state_history` 计数都是 0，提交后各 1 行。

**判据的偏差**：判据写「中途失败后回滚」，实际用的是显式 `tx.Rollback()`——事务语义相同，但没有做故障注入（例如让第二条语句违反约束）。所以它证明的是「两表在同一事务里」，不是「失败路径一定能正确回滚」。

### V7 capability 规模 — 推演过

13 台设备（6 台可写 + 7 台只读上报），每台 3–4 个 capability：

- `capability_state` ≈ **45 行**；
- 单类型最多的是空调：开关、模式、目标温度、风速、摆风、温度回显 = **6 条**；
- `item_type` ≈ 8–10 条（灯、空调、窗帘、加湿器、净化器、温湿度、人体、门磁、扫地机）。

远低于「单类型 > 30 条才拆表」的阈值，维持 `item_type.capabilities` jsonb 不拆。

### V9 E1 演示可行性 — 过

一阶惯性 `dT/dt = k(target − T)`，k = 0.15/分钟，纯 Go 无依赖：

```
[AC]        0min=32.0  10min=27.3  30min=26.1  (目标 26)
[AUTO-OFF]  关空调前=26.0  30min后=32.9   (回升说明策略生效且可见)
[NIGHT]     0min 人体传感器触发，夜灯 8%/2700K 打开
[NIGHT]     3min 延时 3 分钟到，夜灯关闭
V9 OK: 三个场景在「快进」条件下都可被看到
```

结论：室温收敛在 30 分钟内可见，无人自动关空调后的回升可观测，夜起延时关灯按时间线可逐步看到。**E1 不需要等真实时间**，一个 `POST /api/sim/tick?minutes=N` 就能推进。

**与 spec 的偏差**：spec 写「约 30 行」，实际约 90 行（多了两个场景的演示与断言）。功能范围未变，属于行数估算不准。
