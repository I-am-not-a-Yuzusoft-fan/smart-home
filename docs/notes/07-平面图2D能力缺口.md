# 07 · 平面图 2D 能力缺口：对着三份开源实现逐项清算

> 用途：给「平面图编辑器还缺什么」定一份可执行的补课清单，避免凭印象加功能。左栏是三个开源实现的**源码事实**，右栏是我们 `frontend/src/pages/PlanPage.tsx` 的现状。
> 取材（只读，均为 2026-11-23 取）：Sweet Home 3D trunk **r9047**；`charmlinn/blueprint3d-modern` **@f56f0b2**；`cvdlab/react-planner` **@efa710e**。文中的 `文件:行` 都是指向这些固定版本的 permalink，可点。
> 判定口径：**P0** = 不补就会在「画完一套完整户型图」的过程中卡住，或者每加一个新功能都要重写三遍；**P1** = 明显更顺手、评审时一眼能看出差距；**P2** = 锦上添花，或要动数据模型/后端、本课设周期内不划算。
> 引用规则：每条「参考实现有 X」都能指到代码行；指不到的一律标「**未在源码中确认**」，不编。

## 1. 结论摘要

- **值得做（P0，五件事；表里占 7 行）**：①多选 + 框选 + 批量移动（同一件事的三个面）②复制/就地复制 ③画布旋转手柄 ④标尺与坐标读数 ⑤用户可创建的尺寸标注。它们共同指向一件事——**把「单选 + 事后改数字」升级成「选择集合 + 直接操纵 + 可度量」**。
- **可做可不做（P1）**：无限对齐线、手动参考线、自由文字、指北针、按比例打印/PDF、墙的分割/合并/反向、绘制期浮层输入、键盘微调。**（P2）**：翻转、标注样式、房间标签拖位、楼层、房间手绘、单位切换、底图裁剪锁定、DXF/SVG。
- **不做**：3D 视图与光照、灯光功率、家具 3D 模型与材质、文字俯仰、照片/视频渲染、云同步。
- 我们的 2D **深度**其实已反超两份 Web 参考实现：弧墙（SH3D 有 `arcExtent`，BP3D/RP 都没有）、房间自动推导 + 面积 + 用途（RP 是手绘多边形、BP3D 的 `Room` 连面积都没有）、底图两点定标、自动尺寸链。
- 我们缺的是**编辑框架的广度**（选择 → 批量 → 变换）和**图面产出**（标注对象、打印）。这两块恰好是评审时「看起来专业」的部分。
- 一句话路线：**先把三个单选 state 收敛成选择集合，再补「直接操纵」（旋转手柄、可拖尺寸），然后补撑场面的标尺与按比例打印；对齐线/参考线作为 P1 快速跟进。**

## 3. 重点缺口细讲

### 3.1 多选与框选：一切批量操作的地基

**为什么重要。** 复制、批量改厚度、对齐、批量删、一起转，全都挂在「选择集合」上。我们现在三个独立的单选 state 意味着：以后每加一个批量功能，都要在墙/物品/房间三条分支里各写一遍，还会出现「选中墙时物品高亮没清」这类交叉 bug。

**参考实现怎么做。** SH3D 在按下鼠标的那一步就把语义分清楚：手上有物件且没按 Shift → 移动；否则 → 框选。框选是一个独立的 controller state，自己画矩形、自己算相交。

### 3.2 尺寸标注必须是「对象」，不是「推导结果」

**为什么重要。** 现在的尺寸链是 `collinearRuns(walls)` 派生出来的，只能标共线墙，且位置由「下方/左方」硬编码。但真实图纸要标斜边、标门洞定位、标局部净距，还要能把标注拖开避让家具——这三件事派生做不了，因为它们**没有身份**。

**参考实现怎么做。** SH3D 的 `DimensionLine` 是一等模型对象，两端点 + 一个 `offset` 就是全部语义；选中后在 offset 位置出一个可拖手柄，拖拽由专门的 state 处理。

### 3.3 无限对齐线与手动参考线：把吸附从「12px」提升到「设计意图」

**为什么重要。** 现有吸附保证的是「点对点」；但画一排柜子、一排插座时，作者需要的是「这三个东西在同一条竖线上」的视觉反馈——那是一条**穿过全图的线**，不是一个点。

**参考实现怎么做。** RP 给每个顶点生成两条**无限线**（不是线段），线用 `ax+by+c=0` 表示；另外 guide 之间还会两两求交、把交点也变成吸附点。

```js
          addPointSnap(snapElements, x, y, 10, 10, vertexID);
        }
        if (snapMask.get(SNAP_LINE)) {
          ({ a, b, c } = GeometryUtils.horizontalLine(y));
          addLineSnap(snapElements, a, b, c, 10, 1, vertexID);
          ({ a, b, c } = GeometryUtils.verticalLine(x));
          addLineSnap(snapElements, a, b, c, 10, 1, vertexID);
        }
      });
```

```js
// 出处：utils/geometry.js:42-48（efa710e）
export function horizontalLine(y) {
  return {a: 0, b: 1, c: -y};
}
export function verticalLine(x) {
  return {a: 1, b: 0, c: -x};
```

**我们要做什么。** `snap.ts` 的 `Guide` 判别联合已经预留了扩展位，加两档：`{kind:'line', axis, at}`（由所有端点投影生成）与 `{kind:'guide', ...}`（用户手动拖出、存 `plan_meta.guides`）。优先级排在 point/segment 之后，命中时渲染虚线。**别做** RP 那种把 guide 两两求交再变吸附点——复杂度上去了，收益很小。

### 3.4 画布旋转手柄

**为什么重要。** 现在旋转只有属性面板里 `step={90}` 的数字框：沙发想斜 30° 靠角，得开面板、敲数字、点应用。这是最典型的「功能有、手感没有」。

**参考实现怎么做。** RP 用鼠标相对物件中心的角度算 rotation，再在 0/±90/±180 附近 ±5° 内吸附。注意它的吸附是**硬编码四个角度**，不是 15° 网格。

```js
// 出处：class/item.js:159-175（efa710e）
  static updateRotatingItem(state, x, y) {
    let {rotatingSupport, scene} = state;
    let layerID = rotatingSupport.get('layerID');
    let itemID = rotatingSupport.get('itemID');
    let item = state.getIn(['scene', 'layers', layerID, 'items', itemID]);
    let deltaX = x - item.x;
    let deltaY = y - item.y;
    let rotation = Math.atan2(deltaY, deltaX) * 180 / Math.PI - 90;
    if (-5 < rotation && rotation < 5) rotation = 0;
    if (-95 < rotation && rotation < -85) rotation = -90;
    if (-185 < rotation && rotation < -175) rotation = -180;
    if (85 < rotation && rotation < 90) rotation = 90;
    if (-270 < rotation && rotation < -265) rotation = 90;
```

顺带看一眼 SH3D 按下分派的上文（`PlanController.java:9598-9607`）：尺寸线的抬高、家具名的偏移与旋转、指北针的旋转与缩放，**每类对象都配了独立的手柄状态**——直接操纵是 SH3D 的组织原则，旋转手柄只是其中一条。

**我们要做什么。** 选中物品画一个手柄 `Circle`，拖动时 `atan2` 求角，**吸附 15°**（比 RP 的 90° 更实用；Shift 关闭吸附）。落库仍走现有的 `PUT /api/plan` 整份快照，`rotation` 字段已经存在（`client.ts:259-275`），后端不用改。

### 3.5 标尺与坐标读数

**为什么重要。** 没有标尺，画布就没有绝对参照——所有精确尺寸只能事后在面板里核对。而且标尺是「专业感」最廉价的一件东西：两天的工作量，观感提升最大。

**参考实现怎么做。** SH3D 把标尺做成 `PlanComponent` 的内部类，横向一个、纵向一个，各自跟着鼠标画一条游标线；RP 用 HTML 元素，刻度宽度 = `unitPixelSize * zoom`，随缩放重排，鼠标位置用一个小三角标出来。

```java

    private int   orientation;
    private Point mouseLocation;
    public PlanRulerComponent(int orientation) {
      this.orientation = orientation;

```

```js
// 出处：components/viewer2d/rulerX.jsx:42（efa710e）
left: this.props.zeroLeftPosition + (this.props.mouseX * this.props.zoom) - 6.5,
```

**我们要做什么。** 两个绝对定位的 HTML 条（不是在 Konva 里画，省得跟着视口变换算两遍），刻度 = `1m * viewport.scale` 自动挑「整数档」（1m/2m/5m），鼠标移动时把世界坐标写回状态栏（单位 mm）。**顺带收益**：有了标尺，「从标尺拖出参考线」（3.3）就有了自然的入口。

| --- | --- | --- | --- |
| 3D 视图 / 光照 / 相机 | BP3D 的「平面图」是 three.js 场景（[`three/floorplan.ts:7`][bp-three] `FloorplanThree`，用 `WebGLRenderer`）；真正的 2D 是另一条 Canvas2D 管线（[`floorplanner_view.ts:50`][bp-ctx]） | 它画的是俯视平面，和 2D 画布长得一样 | 两条渲染管线 + 两套坐标与命中测试，统一成本远大于收益；课设评分点不在渲染。**2D 画布也不该为 3D 预留抽象**——真要 3D，另起一层读同一份 `Plan` 数据 |
| 灯光功率 | SH3D [`HomeLight.getPower():171`][sh3d-light]；2D 里只是选中灯时画一个 `IndicatorType.CHANGE_POWER` 手柄（[`PlanComponent.java:4576`][pc-power]） | 手柄长在平面图上 | 它调的是 3D 渲染亮度，2D 里没有「功率」这个可观测量。若以后要「照度热图」，那是另一套计算，不是这个手柄 |

| 楼层标高 | SH3D [`Level.getElevation():113`][sh3d-level] | `MultipleLevelsPlanPanel` 是 2D 标签页 | 2D 里它退化成「图层」；我们真需要的是图层，不是标高。真要楼层，成本在后端主键与迁移 |
| 照片 / 视频渲染 | SH3D `PhotoController` / `VideoController` | — | 纯 3D 出图 |
| 云同步 / 协作 / 账号 | 三份参考实现都没有（SH3D 是桌面单机 + 本地文件） | — | 不在课设范围；单机并发 `plan_meta.version` 已经够用 |
| 家具目录 / 在线模型库 | SH3D 的 `FurnitureCatalog` | 家具是 2D 里画的 | 我们是设备库不是素材站；当前 `item_type` + `capability` 的抽象更贴合智能家居 |

## 5. 未在源码中确认的（别照着做）

- **「对齐 / 分布」命令**（选中多个 → 点按钮对齐左边缘 / 等距分布）：三份参考实现都**没有**这种按钮式命令。SH3D 只有拖拽期的对齐引导（[`9786`][sh3d-align]），RP 只有无限线吸附。行业里确实标配，但**没有开源实现可抄**，要自己设计交互（建议：与多选一起做，用 Shift 临时压住吸附）。
- **DXF / SVG 导出**：三份都没有可抄的实现（SH3D 的导出路径是 OBJ/DAE/PDF）。
- **楼梯 / 洁具的 2D 符号库**：SH3D 的楼梯是 3D 家具模型，2D 只是投影；没有独立的符号体系。我们要做的话是自己画一套 Konva `Group` 图标，没有参考。
- **框选在 RP 里的实现**：`viewer2d/viewer2d.jsx` 里没有 shift / marquee 分支，多选靠侧栏勾选。所以「RP 有框选」这个说法不成立。
