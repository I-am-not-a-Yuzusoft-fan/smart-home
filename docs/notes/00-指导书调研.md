# 指导书调研

> 依据：`课程设计书/2026智能家居系统-课程设计指导书.md`（2026-11-19 由 docx 逐段转换，正文一比一保留）。
> 本文做两件事：把指导书里的硬性要求摊平成可核对的清单；核验其中可由外部事实验证的部分。

## 1. 一句话概括

3～4 人一组，8 周内做一个**可运行、可演示、架构清晰**的智能家居 Web 系统，走通「建图 → 布家具 → 控制 → 看状态 → 触发场景」；**分层架构是强制项，也是最大分值来源**。

| 编号 | 功能 | 验收判据（原文） | 实现要点 |
| --- | --- | --- | --- |
| F1 | 家居物品管理 | 物品与设备增删改查；属性含名称、类别、所属房间、坐标、状态；按房间/类别筛选 + 关键字搜索；JSON 或 CSV 批量导入导出；坐标改动必须落到数据层 | 坐标与属性统一入库，不能只活在前端 state |

| F3 | 平面图绘制与布放 | 绘制墙体（建议网格吸附与端点捕捉）；拖拽家具并支持移动/旋转/删除；选中可查看编辑属性；刷新后恢复 | 平面图数据以 JSON 整体存取 |

| F5 | 一键控制策略 | 回家/离家/睡眠 3 个模式；每模式 = 条件 + 动作集，动作可带参数与延时；**不能机械设温**，须按季节与室内外温度动态计算目标温度；支持滞回；执行有过程反馈 | 见下方评分区分点 |

### F5 评分区分点（原文，务必照做）

- 代码里写死 26℃ 只能拿基础分。
- 把「舒适」作为调控目标：输入季节、室内外温度、湿度，算出目标温度并限制区间——
  - 夏季舒适区间 **24～28℃**
  - 冬季 **18～22℃**
  - 春秋过渡季优先建议自然通风
- 启停阈值设 **1℃** 缓冲区间，避免阈值附近反复启停。
- 每次自动调节附带依据说明，例：「当前室温 32℃、湿度 75%，按照夏季温控策略，设定目标温度 26℃」。

| 编号 | 功能 | 要点 | 加分抓手 |
| --- | --- | --- | --- |
| E1 | 房间环境感知与自适应 | 温度/湿度/光照/人体存在；低于阈值自动开灯、高湿自动除湿、无人自动关闭；处理多目标冲突并说明决策规则；支持手动接管（用户操作后策略暂时让位） | 冲突仲裁规则 + 手动接管状态机 |

## 5. 架构是硬指标

**强制分层，这是核心考察点。** 推荐五层，依赖方向必须单向：

| 层次 | 职责 | 不该做的事 |
| --- | --- | --- |
| 展示层 | 渲染平面图/3D、采集操作、展示状态 | SQL 拼接、业务规则实现 |
| 策略层 | 把「意图」翻译成「设备指令集」；规则求值；环境自适应 | 关心设备协议、直接操作数据库 |
| 控制层 | 指令校验、编排、下发、重试、状态回写与广播 | 写业务规则（「夏天设几度」不属于这层） |
| 设备层 | 设备能力描述、命令执行、状态上报 | 感知房间与用户 |
| 数据层 | 持久化、查询、事务、缓存 | 业务判断 |

依赖流向：**展示层 → 策略层 → 控制层 → 设备层**，数据层被各层以接口方式依赖。禁止反向依赖，禁止跨层调用。

### 四条设计原则

1. **关注点分离**——策略只回答「该做什么」，控制只回答「怎么可靠地做到」，设备只回答「能不能做」。
2. **面向接口**——层间通过接口通信，便于把模拟器换成真实设备。
3. **配置驱动**——设备类型、场景策略用配置描述，减少硬编码分支。
4. **单一数据源**——设备状态以服务端为准，前端只做投影与缓存。

### 数据模型：类型—能力—状态 三层

核心不是表有多少张，而是**设备建模是否有抽象**。

- **设备类型**：一类设备有哪些能力，如空调 = `{power, mode, target_temp, fan_speed}`。
- **能力**：单个可读写属性的元数据——键名、数据类型、取值范围、单位、是否可写。
- **设备实例**：类型的具体化，持有当前状态与在线状态，绑定到某个家具或房间。

做到这一层，**新增设备类型只需注册能力描述**，控制层与展示层无需改动（这也是加分项之一）。命令与状态建议统一为带 `deviceId`、`capability`、`value`、`requestId` 的报文结构。

## 6. 可量化的非功能指标

| 维度 | 指标 |
| --- | --- |
| 性能 | 平面图 50 件家具内操作 ≥30 FPS；控制指令端到端 ≤1s（局域网）；首屏 ≤3s |
| 可靠性 | 服务异常不丢数据；命令失败可重试；关键操作有日志 |
| 可用性 | 主要功能 3 次点击内可达；错误提示可理解；支持 Chrome / Edge 最新版 |
| 安全性 | 登录（单用户口令或简单账号体系即可）；接口参数校验；敏感配置不入库不入仓 |

### 10.2 许可证：这是最大的问题

**该仓库没有任何许可证。**

- 根目录无 `LICENSE` / `LICENSE.md` / `NOTICE`
- 根 `package.json` 与 `frontend/package.json` 都没有 `license` 字段
- 全仓库源码、配置、文档中 0 处 `copyright` 字样
- README 未声明来源、未声明衍生关系、未提第三方素材署名

后果：公开可见 ≠ 获得授权。无许可证默认「保留所有权利」——可以浏览、可以在 GitHub 内 fork，但**复制、修改、再分发都没有被授权**。

这让指导书 4.4 那句「使用开源代码须遵守其许可证并在文档与致谢中注明来源」在此项目上无对象可遵守，也让 4.1 的「可直接复用」与 1.2 的「不允许套用现成平台换皮」正面冲突。指导书默认 Home3D 是「开源的」，这个前提本身不成立。

（以上是事实核验，不是法律意见；真要复制代码，须先取得作者书面授权。）

### 10.5 对路线选择的影响

| 路线 | 技术可行性 | 许可证风险 | 额外代价 |
| --- | --- | --- | --- |
| A. iframe 嵌入 | 可行，Home3D 是纯前端应用 | 低（未复制代码） | 双份状态、postMessage 通信、无法接入自己的五层架构 |
| B. Fork 改造 | 可行 | **高**（复制即侵权，且 1.2 明令不许换皮） | 1443 行的 `Canvas2D.jsx` 是结构债，改造量大 |
| C. 复用引擎 | 可行（621 行纯函数） | **高**（同样是复制） | 需自建 schema 与 UI |

三条路线里 B 和 C 都建立在「可以复制这份代码」的前提上，而这个前提没有许可证支撑。折中做法是**读它的算法自己重写**（思路不受版权保护，表达受保护），代价是工作量上升但风险归零。

**已决：走自研，只借鉴思路。** 用 TS + three.js + r3f 重写平面图与 3D 视口，把 Home3D 当作设计参考而非代码来源（其「同一份设计数据、2D 与 3D 两个投影」的范式值得照抄，代码不值得）。Fork 与复用引擎两条路放弃，理由是许可证缺失、且其 4120 行前端零 TypeScript、无 API 层，改造量不低于自研。
