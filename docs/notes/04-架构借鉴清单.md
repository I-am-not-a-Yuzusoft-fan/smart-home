# 04 · Home Assistant 架构借鉴清单

> 前置：需求见指导书 2.1 / 2.2 / 3.4；scene / script / automation 三分法与 target 寻址见 [`02-Home-Assistant-参考.md`](02-Home-Assistant-参考.md)；device / entity 分层与「语义采用、存储不拆」见 [`03-HA-设备与实体模型.md`](03-HA-设备与实体模型.md)。本文不重复它们，只回答三件事：机制要不要抄、接缝留在哪、扩展点现在加还是以后加。
> 核对时间：2026-11-20。一手来源限定为 contributors 站点、`home-assistant/core` 的 `dev` 分支、`home-assistant/architecture` 的 ADR 与开发者博客、PostgreSQL 17 官方文档。

## 1. 一句话结论

HA 值得抄的是**「一个真相源 + 一处写入 + 多个互不认识的消费者」这条拓扑**，不是它的机制清单。registry、config entry、recorder 这三层是它为「多个第三方集成、数千万家庭、十年升级」付的税；我们的规模（1 个家庭、18 台设备、3 人、3 周）交不起也不该交。决定后期是否返工的不是「表够不够多」，而是**键是否稳定、写入点是否唯一、数据能否一次性重建**——三者现在都能以接近零的成本锁死，而「多建表」既买不到它们，还会额外欠下维护债。

## 2. HA 架构机制逐条评判

判定口径：**现在要** = 直接影响评分点或本周就要写；**留接缝** = 现在不建，但把将来能接上的位置定死；**永远不要** = 它是为 HA 的前提付的税，我们不共享那个前提。

| 机制 | 解决什么问题 | 成本 | 我们要不要 | 接缝在哪 |
| --- | --- | --- | --- | --- |
| 事件总线 + 内存状态机 | 让「谁改了状态」与「谁关心状态」解耦；进程内状态机即真相 | 自研 pub/sub 约百行；但「内存为真相」与 DB 真相源直接冲突 | 不要状态机；要一个进程内广播点 | 控制层写库成功后调用单一 `Broadcaster` 接口 |
| Recorder + 长时统计 | 高频状态落关系库而不拖慢主循环；明细与聚合分离 | 独立写入线程、批量刷盘、purge、`state_class` 语义、统计表 | 明细要（`state_history` 已定）；批量与统计不要 | `state_history` 只追加，按 `(item_id, capability_key, recorded_at)` 建索引；聚合以后建物化视图 |
| Config entry / 集成插件 | 多实例配置、版本迁移、失败重试、卸载清理 | 七态机 + `unique_id` + 迁移钩子 + reload 语义 | 永远不要 | `item_type` 上一个 `driver` 字段，或控制层 `Adapter` 接口按类型分派 |
| Domain + Platform + `supported_features` | 同类设备统一接口，前端按 domain 渲染控件 | 每个 domain 一套基类；位图只能表达「有没有」 | 语义要，类与位图都不要 | capability 元数据的 `type / options / min / max / unit / writable` 驱动渲染与校验 |
| device / entity / area / floor / label 五 registry | 分离「集成上报」与「用户改动」，用户值胜出并跨重启保存 | 每类一张表 + `original_*` 覆盖列 + 级联禁用/删除 | 不要（唯一供给方是模拟器）；房间一个字段就够 | 将来真需要「用户改名 vs 上报名」时，加 `name_override` 单列，不建整表 |
| service（action）注册表 + target | 调用方不认识被调用方；一处做校验、权限、target 展开 | 注册表 + 四类 target 解析 + 权限检查 + `call_service` 事件 | 不要 | 控制层单一 `Execute(cmd)` 入口 + `Command` 值对象（指导书 3.4 的报文已把它定死） |
| 模板（Jinja）+ 模板实体 | 派生值声明式定义，依赖变了自动重算 | 表达式引擎、依赖追踪、更新限流 | 永远不要 | 策略层纯函数返回「目标值 + 依据字符串」，依据用格式化拼，不引模板语言 |
| `.storage/` 的 JSON `Store` | 非关系型小配置落盘，带版本迁移与合并写 | 文件锁、原子写、版本迁移 | 永远不要（会变成第二个真相源） | jsonb 列内带 `version` 键，读时按版本升级 |
| `RestoreEntity` | 内存状态机重启即失忆，需要把上次状态写回 | 一次全量状态落盘 + 版本兼容 + 索引键设计 | 永远不要 | 无——它是「内存为真相」的补丁，我们不引入这个前提 |
| `DataUpdateCoordinator` | 轮询去重；失败时统一 `unavailable`；错误处理集中一处 | 调度器、退避、可用性状态机 | 机制不要，语义要 | `capability_state` 的 `updated_at` + `source`，读层据此判 stale |
| WebSocket API | 前端订阅增量，不必轮询 | 握手、订阅协议、消息压缩编码 | 要（`/ws/state` 已定）；压缩编码不要 | 消息 envelope 固定 `type` + `id`，payload 以后可整体替换 |
| 场景快照（`scene.create`） | 把当前状态存成可重放集合 | 快照表 + 与实体状态的一致性检查 | 现在不要（F5 走 script 语义，见 02 文档 §6） | 快照 = 一组 `(item_id, capability_key, value)` 行，与 `capability_state` 同构，加表零成本 |
| Blueprint | 参数化复用他人写的自动化 | 参数模式 + selector + 导入链接 | 永远不要 | 无（3 人共享一个仓库，没有生态可言） |
| 多租户 / 用户与权限 | 多用户隔离与授权；每次调用带 `Context.user_id` | policy 字典 + 每个调用点检查 + owner 例外 | 多租户机制不建（接口靠 store 层 + UUID 主键预留）；账号与角色要（指导书 2.3「安全性」明写登录） | `state_history.source` 已能支撑 E1 的「手动接管让位」；真做多用户时加 `created_by` 单列 |

### 2.1 值得抄的是三条语义，不是三个组件

1. **单一真相源 + 单一写入点 + 互不认识的消费者。** HA 原文是「None of these parts know about each other. They meet in the state machine and on the event bus.」（[Core 概览](https://contributors.home-assistant.io/architecture/core/)）。这条拓扑我们可以原样搬：控制层写库成功 → 单一广播点 → WS 消费者，消费者之间不互相调用。**不要**搬它的状态机——HA 的前提是进程内状态机即真相，我们的前提是 DB 即真相（指导书 3.2「单一数据源」），把两者叠起来等于给 F4 的「三处一致」加第三个可漂移副本，还得再造一个 `RestoreEntity` 去补重启后的洞。
2. **失败时标 `unavailable`，绝不展示编造或过期值。** 「They never show made-up or stale values.」（[Getting data](https://contributors.home-assistant.io/architecture/core/data-updates/)）。F4 要求「命令需有成功/失败/超时反馈」，这条语义直接就是评分点：状态带 `updated_at`，超出窗口没更新就标不可用，而不是继续显示上一次的值。
3. **先发全量再发增量，消息带 `id` 与 `type`。** `subscribe_entities` 订阅时先发全部可见状态，之后只发变更（[WebSocket API](https://contributors.home-assistant.io/core/internals/websocket-api/)）。`/ws/state` 已在 ADR 0001 定下，这条不算新增工作；18 台设备抄这个手感是对的：前端拿到连接即可渲染，不需要额外的「先拉一次快照」接口，也就少一处三处不一致的来源。它那套 `a`/`c`/`r` 压缩字段不要抄——省的是带宽，付出的是调试可读性，我们两样都不缺。

### 2.2 留接缝的三处，以及为什么不现在建

- **长时统计。** HA 的统计是刚需，因为它的历史默认只留 10 天（`purge_keep_days`），而长期曲线要永久保留，所以必须另存每小时聚合（[History and statistics](https://contributors.home-assistant.io/architecture/core/history/)）。F4 只要「历史曲线」，我们不删数据就没有这个需求。接缝是索引：`state_history` 的索引顺序一旦按 `(item_id, capability_key, recorded_at)` 建好，将来加物化视图或统计表不需要改动任何写入路径。
- **场景快照。** 它和 `capability_state` 同构（一组「数据点 → 值」），所以只要 `capability_key` 稳定，快照表随时能加。这正好是「留接缝 ≠ 现在建表」的样板。
- **用户与权限。** 指导书 1.2 明说多租户可以不做；2.3 只要求「登录（单用户口令或简单账号体系即可）」。一个口令 + 一个会话就够，`user_id` 列现在加只是噪音。真要做时是加 `created_by` 一列，不是全表改造——前提是主键不是「用户内自增」这种带租户语义的键（见 §3.6）。

### 2.3 「永远不要」的共同前提

`config entry`、五个 registry、`RestoreEntity`、`.storage` 文件，四者都在回答同一个问题：**当「集成上报」与「用户改动」两份数据都有权写同一属性时，谁赢、怎么持久化、重启后怎么恢复。** HA 的答案是 registry 分层 + `original_*` 覆盖 + `restored: true` 占位（[Registries and storage](https://contributors.home-assistant.io/architecture/core/registries/)）。我们只有一个设备供给方（模拟器），用户也只能在同一个前端改，两份数据从不同时存在——这套机制没有作用点，抄过来只会多出一张永远和 `item_type` 打架的表。`03` 文档 §7 已给出升级触发条件（真需要按数据点单独改名/授权，或同一设备被两个来源同时供给时再拆），沿用即可。

## 3. 数据层扩展点：现在留 vs 以后留

每条的格式是：**现在加的成本 / 以后再加的成本 / 建议**。

### 3.1 `tenant_id` / `user_id` —— 不加

- **现在加**：一列 + 每条查询带过滤条件 + 每个唯一键改成 `(tenant_id, ...)`。看似零成本，真正的成本是纪律：漏一个 `WHERE` 就是越权，而这类漏在演示时不会暴露。
- **以后再加**：只要主键是全局唯一的（UUID），加 `tenant_id` 只是加一列默认值 + 加过滤条件，不需要重建约束。**反过来说，如果用「租户内自增」的整数主键，以后加租户要重建所有唯一约束与全部外键。**
- **建议**：不加。可扩展性在这里由**键的选择**决定，不由列的多少决定——这是本节最重要的一条。
- **注意区分「不加列」与「不预留」**：不加 `tenant_id` 不等于不预留多租户接口。预留的方式是**数据访问一律经 `backend/store` 一层**（不裸露 SQL）+ **主键全局唯一**（§3.6），届时加一列默认值加过滤条件即可，既不重建约束也不用全表改造。反过来，把「租户内自增」这种带租户语义的整数主键选上，才是真的把路堵死了。

### 3.2 capability 单独建字典表 —— 不建，只放 `item_type.capabilities` 的 jsonb

- **现在建**：一张表 + 外键 + 读一条设备状态要 type→capability→state 两跳 join；前端要为「表单元数据」和「当前值」分别取两个接口，多一处可不同步的地方。
- **以后拆**：全部数据是 18 台设备 × 约 5 个 capability ≈ 90 行，从 jsonb 拆表是一个脚本加一次回填，不到一小时。
- **建议**：jsonb。判断依据是**读的人怎么读**：capability 元数据的唯一消费者是「按类型整取」的前端表单渲染器和后端校验器，没有任何「按 capability_key 全局查询」的需求（F5 的动作集是「房间 ∩ 类型」，走 `item_type` 就够）。指导书 3.4 的原文也是「能力：描述单个可读写属性的**元数据**」——它是描述，不是实体。建表还会立刻制造二次真相：jsonb 里一份、表里一份，谁赢说不清。
- **唯一硬约束**：`capability_key` 一旦写进 seed 就不得重命名。理由见 §4 的 `restore_state` 案例——身份键选错要迁移。

### 3.3 通用 `attribute` EAV 表 —— 永远不要

- **现在加**：一张 `(item_id, key, value text)` 表 + 每次读要 pivot + 类型全丢（数字、布尔、枚举都退化成字符串）+ 导入导出要重建结构 + 前端要自己猜类型。
- **以后改回**：从 EAV 回到强类型列是灾难级迁移，而且历史数据已经丢了类型信息。
- **建议**：用两层替代。**`capability_state`（强类型、可写、有历史、能触发策略）** 与 **`item.attrs` jsonb（展示型、低变化、无历史，如尺寸/材质/图标变体）** 严格二分。判据一句话：**需要曲线、需要策略读、需要命令写的，进 `capability_state`；只影响怎么画、不值得记历史的，进 `item.attrs`。** HA 的原则页对此有同向表态：「If no platform fits … don't work around it with attributes」（[Principles](https://contributors.home-assistant.io/architecture/principles/)）——属性是补充位，不是状态位。

### 3.4 事件表（event log）—— 加一张，但只加 `command_log`

- **现在加**：一张九列表（`request_id / item_id / capability_key / value / status / error / source / created_at / completed_at`）+ 一个写入点。
- **以后再加**：失败的命令不产生任何 `state_history` 行——只靠状态变化永远补不出「谁在什么时候试过、为什么失败」。等答辩被问「超时怎么证明」时再补，就要回头改控制层的每个分支。
- **建议**：**现在就加，这是本文唯一建议新增的表。** 理由是它直接对应评分点：F4 明写「命令需有成功/失败/超时反馈」，E4 要求「为什么这么做」的解释。而 `state_history` 的语义是「值变了」，命令日志的语义是「尝试了一次，可能失败」，两者不能混表。反过来，**不要**建通用 event log（HA 的 recorder 连事件一起存，是它 schema 债的主因，见 §4.1）。

### 3.5 `state_history` 分区与保留 —— 不分区，只留一条清理语句

- **现在分区**：PostgreSQL 的分区表上「唯一约束（因而主键）的列必须包含全部分区键列」（[PG17 §5.12.2.3 Limitations](https://www.postgresql.org/docs/17/ddl-partitioning.html)）。按时间分区就意味着主键必须变成 `(id, recorded_at)`，还要加分区维护任务。为一个演示库引入这套，成本远超收益。
- **以后再加**：量级估算——若约 10 个数据点以 10 秒间隔变化、每天活跃 8 小时，约 8.6 万行/天、三周约 180 万行；PG 单表加对索引完全无压力。真到需要分区时，是一次「建新表 + copy + rename」的迁移，或者干脆一次性重建历史。
- **建议**：不分区。只做三件事：`(item_id, capability_key, recorded_at DESC)` 索引；一条按 `recorded_at < now() - N 天` 的删除语句（N 写进配置）；**`state_history` 不要对 `item` 建外键**——删设备时历史应保留，历史是只读日志，悬挂的 `item_id` 比被级联删掉的历史有价值。HA 的 recorder 走的是另一条路：`entity_id` 归一到 `states_meta`、属性归一到 `state_attributes`，`states` 只留 `metadata_id` / `attributes_id` 两个外键，为的是状态行不重复存字符串（[`db_schema.py`](https://github.com/home-assistant/core/blob/dev/homeassistant/components/recorder/db_schema.py)）；它要支撑千万级行才值得这么做，我们 18 台设备直接存 `item_id` 即可。

### 3.6 主键：自增 bigint 还是 UUID —— 分表决定

- **对导入导出**：UUID 让「导出 JSON → 在另一台机器导入」不会撞号，也不依赖序列当前值；bigint 导出后重导必须重映射主键，还要顺带改所有引用它的坐标/快照数据。
- **对演示重建**：bigint + truncate + 重置序列最省事；但**把 UUID 写死在 seed 文件里，重建同样是确定性的**——这条反对意见只在 seed 用随机生成时才成立。
- **建议**：`item` 用 UUID（v4 即可，PG17 内置 `gen_random_uuid()`，见 [PG17 §9.14 UUID Functions](https://www.postgresql.org/docs/17/functions-uuid.html)；v7 在 PG17 上要应用侧生成）。`state_history` / `command_log` 用自增 bigint——纯追加、体量大、只被聚合查询读，bigint 更小更快，且不需要生成器。
- **附带一条**：`item` 删除后 id 不得复用。UUID 天然满足；若坚持 bigint，就不能用「复用最大 id」的写法。

### 3.7 时间戳：一律 `timestamptz`；`created_at` / `updated_at` 不必全覆盖

- **`timestamptz`**：PG 内部按 UTC 存，输出时转成会话时区（[PG17 §8.5.1.3 Time Stamps](https://www.postgresql.org/docs/17/datatype-datetime.html)）。用 `timestamp` 的话，后端容器 UTC、前端 Asia/Shanghai、演示换一台机器，三处会各差 8 小时——而 F4 的「最近更新时间」正好要显示给人看。
- **覆盖范围**：只追加的表（`state_history`、`command_log`）只需要 `recorded_at` / `created_at`；`item`、`item_type`、`room` 需要 `created_at` + `updated_at`。**`capability_state.updated_at` 不是装饰**，它就是 F4 要求的「最近更新时间」，请在建模时当成必填列而不是可选列。
- **建议**：`updated_at` 由写入语句显式赋值，不要用数据库触发器——触发器在 sqlc 生成代码里不可见，三个人排查问题时最容易漏掉它。

### 3.8 schema 迁移做到什么程度算够

- **现在**：`golang-migrate` 已在 ADR 0001 选定，成本为零，**不要退回手写 SQL**——工具的价值不在功能，在 `schema_migrations` 这本账：答辩时能说清第几次改了什么，回归时能 `down` 一步。
- **够用的标准**：① 空库能 `up` 到最新并跑通 seed；② 每个 PR 至多一个迁移文件、一个目的；③ 只保证最近一步的 `down` 可用；④ 不写数据迁移脚本，历史数据靠 seed 重建。
- **纪律**：迁移只做「加表 / 加列（带默认值）/ 加索引」。重命名与删除要写进本文档的负债清单，并留一次发布周期——这正是 HA 给 config entry 定的 minor / major 之分：「A minor version bump is backwards compatible. Only add things that older code can ignore, like a new key with a default.」（[Config entries](https://contributors.home-assistant.io/core/integrations/config-entries/)）它甚至是被逼出来的：在此之前团队长期不敢版本化，只能到处写软升级补丁（[Blog 2023-12-18](https://contributors.home-assistant.io/blog/2023/12/18/config-entry-minor-version/)）。我们一开始就按这个纪律写，比事后补便宜。

### 3.9 现在就该留、且几乎零成本的四项

1. `capability_state` 加 `source`（`manual / automation / device / timeout`）——E1 的「手动接管让位」靠它判定，不靠 `user_id`。
2. capability 元数据里留 `options`（枚举集合）与 `version`（jsonb 结构版本）两个键——前者让 F2 的差异化属性不必硬编码，后者让改结构时可判读。
3. `state_history` 只存变化后的值，不存 attributes 全量快照——HA 的教训是「Every attribute is stored with every state change」，属性随状态全存与它 recorder schema 演进到第 53 版同源（[States](https://contributors.home-assistant.io/core/internals/states/)、[`db_schema.py`](https://github.com/home-assistant/core/blob/dev/homeassistant/components/recorder/db_schema.py)）。
4. `command_log.request_id` 与报文里的 `requestId` 同名同值——前端靠它把「超时」对回到那一次点击，F4 的反馈链路因此闭合。

### 3.10 现在留就会变成负担的四种「过度设计」

1. **软删除（`deleted_at`）**：每条查询都要带 `WHERE deleted_at IS NULL`，漏一处就是幽灵数据；而 `state_history` 本身已保留历史，删设备不影响历史完整性。
2. **每张表一个 `metadata` jsonb 兜底列**：它不解决任何已知需求，只是把「以后可能要用」的焦虑存进数据库；一旦有人写进去，就再没人知道里面该有什么。
3. **把状态枚举一次列到十几个值**：合法值应由 capability 元数据的 `options` 驱动（F2），在 SQL 约束或 Go 常量里写死枚举，等于提前输掉「新增类型不改核心代码」这个评分点。
4. **审计触发器 / 通用变更日志**：三个人三周没人读它；`command_log` 已覆盖唯一有验收要求的场景（F4 的成功/失败/超时）。

## 4. 「最大可扩展」这个准则的反面证据

### 4.1 HA 自己还的四笔债

1. **device 的全局唯一标识被降级。** 曾经用全局唯一的 `identifiers` / `connections` 把多集成发现的同一台设备合并成一个 device；2026.8 起改为「每个 config entry 内唯一」。理由原文：「There's no single source of truth for device information such as name or model; conflicting values are discarded instead of preserved.」，外加「long-standing bugs where modifying the connections and identifiers of a device causes multiple devices to end up with the same connections」（[Blog 2026-07-21](https://contributors.home-assistant.io/blog/2026/07/21/device-registry-single-config-entry/)）。代价是加载时把设备拆分、加只读的 composite device 兼容层、废弃字段支持到 2027.8。
2. **`restore_state` 的索引键换了。** 2026.11 起存的状态从「按 `entity_id` 索引」改为「按 entity registry ID 索引」，因为 `entity_id` 会被重用，旧状态可能恢复到另一台设备上（[Blog 2026-10-06](https://contributors.home-assistant.io/blog/2026/10/06/restore-state-last-states-removal/)）。**这两个案例是同一类错误：身份键选了可变的、可复用的东西。**
3. **config entry 长期不敢版本化。** 团队自述「We have been very conservative with versioning config entry data …」。直到 2023 年才有 minor version（同上 2023-12-18 博客）。说明「先上线再补版本机制」的代价是散落各处的 `dict.get` 软升级。
4. **recorder 的 schema 面积。** `SCHEMA_VERSION = 53`（[`db_schema.py`](https://github.com/home-assistant/core/blob/dev/homeassistant/components/recorder/db_schema.py)），配套 `migration.py` 3347 行，含 live migration、外键重建、时间列迁移（[`migration.py`](https://github.com/home-assistant/core/blob/dev/homeassistant/components/recorder/migration.py)）。更能说明问题的是：`States` 里的 `entity_id`、`attributes`、`last_updated` 都被标成 `UNUSED_LEGACY_COLUMN`（即 `Unused(0)`）留在模型里，真正生效的是后来加的 `metadata_id`、`attributes_id` 与 `*_ts` 列——「先存了、后来发现该归一」的最终形态是**一列都不敢删，新老并存在同一张表上**。这是「事件与状态全存 + 属性随状态全存」的长期代价，不是它做错了，是它必须支持「任意历史数据不丢」。

### 4.2 一个反直觉的证据：成熟项目会主动**减少**灵活性

ADR-0007 的理由是「The multitude of options for config and integration structure makes it: A. Harder for users … B. Harder for contributors … C. Harder for Home Assistant to support …」（[ADR-0007](https://github.com/home-assistant/architecture/blob/master/adr/0007-integration-config-yaml-structure.md)），于是把 YAML 配置方式收敛成唯一一种。原则页也把「Support less, support it well」列为八条原则之一（[Principles](https://contributors.home-assistant.io/architecture/principles/)）。**一个十年、几千贡献者的项目在减少选项；我们三个人三周，没有理由增加选项。**

### 4.3 结论：把「可扩展」换成三条可验收的说法

「最大可扩展」不可验收——没人能证明自己做够了。换成三条能当场检查的：

1. **接缝清单（seam list）**：跨层边界只有指导书 3.1 规定的五层那几个，每个边界一个接口 + 一个实现（目录映射见 ADR 0001）。新增能力只能在边界内侧实现，**不得新增边界**。检查方法：数一遍 `interface` 声明，超过边界数就是过度设计。
2. **可加不可改（additive-only）**：迁移只允许加表、加列、加索引；任何重命名/删除进负债清单并留一个迭代。依据见 §3.8。
3. **一次性数据重建（rebuildability）**：`migrate down → up → seed` 能在十秒内重建全部演示数据（18 台设备、平面图、3 个模式），seed 里的 UUID 写死。这条把「对未来不确定性的保险」从「现在多建表」换成了「现在写一个能重放的脚本」——成本几小时，换来整个学期的试错自由。

**验收题**：明天要加第 14 台设备或第 4 个模式，需要改几张表、几个文件？目标 ≤ 1 张表、0 行前端代码（F2 原话「新增类型不需改前端代码」）。答不上来，说明扩展点留错了位置，而不是留少了。

## 5. 可以直接写进 ADR 0002 的结论

1. 保持单表 `item` + `item_type`，不为 device / entity registry 拆表；升级触发条件沿用 [`03`](03-HA-设备与实体模型.md) §7，不提前拆。
2. capability 只以 jsonb 存在于 `item_type.capabilities`，内含 `version` 与 `options`；不建 capability 字典表。
3. `capability_state` 主键 `(item_id, capability_key)`，并带 `source` 与 `updated_at`；`capability_key` 发布后不得重命名，改名走「新增 key + 迁移 + 保留旧 key 一个迭代」。
4. `item` 用 UUID（v4），`state_history` / `command_log` 用自增 bigint；`item` 删除后 id 不复用。
5. 所有时间列用 `timestamptz`；追加表只有 `recorded_at`，`item` / `item_type` / `room` 有 `created_at` + `updated_at`，后者由写入语句赋值，不用触发器。
6. 现在就建 `command_log`（成功/失败/超时 + `request_id`），不建通用 event log；`state_history` 只存变化后的值，不存 attributes 快照，且不对 `item` 建外键。
7. `state_history` 不分区、不建统计表；只加索引与一条按保留天数的删除语句。
8. 迁移只做 additive；每个迁移文件只有一个目的；保留「空库 up + seed 十秒重建演示数据」的脚本。
9. 不引入内存状态机、`RestoreEntity`、`.storage` 文件、表达式模板——保持 DB 单一真相源。

## 6. 未能确认的问题

- `supported_features` 位标志是否真的因位数不够而改过：**未找到证据**。Python 整数无固定位宽，位的数量本身不会耗尽；更可能的问题是它只能表达「有没有」而不能表达「有哪几个/什么范围」，需要另开属性承载参数——这一点只核到「Each feature is a bit」（[Glossary: supported features](https://contributors.home-assistant.io/glossary/supported-features/)）与其前端渲染行为，未核到官方对表达力不足的表述。
- `recorder` 把 states 与 attributes 拆表，是否有对应 ADR：**未确认**。只在文档层看到「States and their attributes are stored apart, and identical attributes are stored once」，ADR 仓库 22 条中没有对应条目。
- `helpers/entity_component.py` 在 2026 年的现状（是否已废弃、与 entity platform 的关系）：**未读源码**，本文只用文档层的「Each domain is an entity platform」表述。
- 场景快照在实体被删除后的行为（是否自动剔除该实体）：**未读源码**，只核到 `scene.create` 可对 `snapshot_entities` 现场创建（[Scene 集成文档](https://www.home-assistant.io/integrations/scene/)）。
- §3.5 的行数估算是按「约 10 个数据点、10 秒间隔、每天 8 小时」假设推的，**不是实测**；18 台设备实际的 capability 数量与变化频率要等模拟器跑起来才有数。
- device 标识唯一性从全局改为 per config entry，走的是 Discussion #1226 + 开发者博客而**未成 ADR**（[Discussion #1226](https://github.com/home-assistant/architecture/discussions/1226)，另见 [`03`](03-HA-设备与实体模型.md) §5）。
