## 0. 先说一处核实结论：seed 里不是 5 个模式

`sql/seed.sql:102-115` 只有**一个**模式（`回家`，`run_mode='restart'`），`definition` 是 `version:1` + 5 个步骤：`action`（灯 on）/ `action`（brightness 70）/ `delay`（2000ms）/ `action`（窗帘 position 0）/ `choose`（室温 > 28℃ 时开空调，`else: []`）。

没有顶层守卫、没有 `timeout`、没有 `continueOnError`、没有单步 `enabled`、没有 `repeat`/`parallel` 节点。指导书与本仓库文档里说的"5 个场景模板"（`docs/deliverables/03-概要设计说明书.md:626`、`docs/adr/0002-数据模型与分层.md:136`、`docs/deliverables/02-需求规格说明书.md:66`）在 seed 里**没有落地**。

## 1. 结论摘要（10 条，可直接决策）

1. **HA 的 script 模型与本项目票里的设计是同一套语义，不是"有点像"**：`sequence`/`delay`/`choose`/`repeat`/`parallel`/`continue_on_error`/`enabled`/`alias`/`mode: single|restart|queued|parallel`/`max`/`max_exceeded` 在 `homeassistant/helpers/script.py` 里全部有实现与常量（§3.2）。**照抄语义与命名，不要自创。**
2. **"通用步骤编辑器、不收敛成 5 个内置模式"这个决策（issue #1）有上游事实支撑**：HA 把顺序/延时/条件/选择/重复/并行/失败继续/单步开关全部建模成一等公民 building block，而且 **automations 与 scripts 共用同一套**——官方页面标题现在就叫 *Building blocks in automations and scripts*（§3.1）。
3. **1℃ 滞回的工业界做法不是"写死 1℃"**，而是**双向阈值**（`cold_tolerance`/`hot_tolerance`）+ **最小循环时间**（`min_cycle_duration`/`cycle_cooldown`）。HA 默认容差 0.3℃ 而非 1℃；且该集成源码顶部写明 **DEVELOPMENT ... IS FROZEN**——借模型，不借代码（§3.4）。
4. **指导书的 24–28 / 18–22 不是"舒适标准区间"，而是 GB 50736-2012 §3.0.2 表 3.0.2 的"室内设计参数"**，且两端口径不一致：夏 24–28 = 供冷 Ⅰ+Ⅱ 级全区间，冬 18–22 = 供热**仅 Ⅱ 级**。ISO 7730 只给 PMV/PPD 方法、不给这两个数。→ 文档里要写成"**设定值区间 + 策略约束**"，不能写成"国标要求"（§3.5）。
5. **手动接管没有可供照抄的 core 实现**：HA core 只有 `Context.user_id` 这种"来源归因"，成熟参数化实现 `take_over_control` / `autoreset_control_seconds` / `detect_non_ha_changes` 出自 **custom integration** adaptive-lighting。→ **自研**，ADR 0002 的 `source='manual'` 判据够用，但"环境突变解除"需要**手动时刻的读数基线**，DDL 里没有（§3.6）。
6. **F5 后端与契约完成度 = 0**：`backend` 全仓 `grep modes` 为空、`sql/queries` 无 mode 查询、`openapi.yaml` 无 `/api/modes` 等 4 个端点。F5 是"从契约开始"，不是"补实现"。
7. **文档偏移 19 条里 5 条判为"冲突"**，最硬的三条：`run.status` 的 `done` vs DDL 的 `ok`；"模式级守卫不执行并说明原因"在三处设计里**无处安放**；契约路径 `scenes` / `modes` / 不存在 三方不一致（§4）。
8. **Go 侧取舍**：`jsonschema`（santhosh-tekuri v6，Apache-2.0，draft 2020-12，与 openapi 3.1 同方言）**值得引入**用于校验 `mode.definition`；**CEL 不引入**（前端要数据驱动渲染，文本表达式是负担）；**gocron 不引入**（cron ≠ 相对延时）；`errgroup` 已在 `go.sum` 里（`x/sync` 间接依赖），**只在 parallel 节点用**（§3.7）。
9. **编辑器可借 Node-RED 的"状态徽标"**：delay 节点用 `node.status({fill:"blue",shape:"dot",text:队列长度})` 在画布上直接显示排队数。我们的 `run_step` + WS `run_step` 消息已经够，前端只需把它渲染成同款徽标 + 时间线，不必另造进度表（`CONTEXT.md:60` 已定：`run_step` 是过程反馈的唯一依据）。
10. **三件事"改文档先于写代码"**：`03:430` 的 `done`→`ok`；`04:633-636` 追溯表补 FR-5.5/5.6/5.7/5.9 四行；`sql/seed.sql:111-112` 的写死 28℃ 阈值改成 `valueFrom: "comfort"`（否则正好命中指导书"写死 26℃ 只能拿基础分"那条）。

### 3.3 openHAB 与 Node-RED：能借的是呈现与教训，不是执行器

**openHAB**（openhab.org 在本机 TLS 失败，改用同源的 docs 仓库 raw markdown：`openhab/openhab-docs` 的 `src/configuration/rules-dsl.md`、`src/concepts/rules.md`）：

- 规则结构是 `rule "名" when <触发器> then <命令式脚本> end`；延时用 `createTimer(now.plusMinutes(60)) [ ... ]`（`src/concepts/rules.md:626`），阻塞延时直接 `Thread::sleep`。
- **没有声明式步骤树**：没有 `sequence`/`choose`/`delay` 这些节点，条件分支靠 Java 的 `if`。
- 并发语义要自己写：`src/configuration/rules-dsl.md:1026` 的 "Concurrency Guard" 原文——"If a rule is explicitly run from another script, rule, a Main UI widget, etc., instead of a trigger, the rule can be started before the current execution has ended. **借**：①"延时=定时器回调"的思路（Go 里是 `time.Timer` + 选择器）；②"一条规则可能被二次进入，因此必须显式定义并发语义"这个教训——正好对应 SRS 里"同一场景被重复触发：默认重新开始，并可配置为忽略"。**不借**：命令式 DSL 与线程模型。

### 3.4 空调滞回：`generic_thermostat` 的真实写法

`homeassistant/components/generic_thermostat/climate.py:601-613`（tag 2026.11.3）：

```python
too_cold = self._target_temp > self._cur_temp + self._cold_tolerance
too_hot = self._target_temp < self._cur_temp - self._hot_tolerance
now = dt_util.utcnow()

if self._is_device_active:
    if (self.ac_mode and too_cold) or (not self.ac_mode and too_hot):
        # Make sure it's past the `min_cycle_duration` before turning off
        if (
            self._last_toggled_time + self.min_cycle_duration <= now
            or force
        ):
            await self._async_heater_turn_off()
```

开机方向（`:631-633`）镜像：`elif (self.ac_mode and too_hot) or (not self.ac_mode and too_cold)`，门控是 `self._last_toggled_time + self.cycle_cooldown <= now`。

要点：

1. **滞回是"双向阈值"**，不是单阈值加 1℃：制冷（`ac_mode`）时"太冷"= 室温低于目标−容差 才关机，"太热"= 高于目标+容差 才开机。
2. **还有最小循环时间**：`min_cycle_duration`（最短开机）与 `cycle_cooldown`（最短关机），未到时间会 `async_call_later` 排一个复查。这一条比纯滞回更能防"阈值附近抖动"。
3. **还有 keep_alive**：`called_by_timer` 时强制开机（`:622-627`），防设备自己掉线。
4. 默认容差 **0.3℃**（`components/generic_thermostat/const.py:44` `DEFAULT_TOLERANCE = 0.3`），配置键是 `cold_tolerance`/`hot_tolerance`（`:21`/`:23`）——**没有 `heat_tolerance` 这个选项**（社区常这么叫，但代码里不存在；全仓库 grep 0 命中）。
5. 该集成**已冻结**：`const.py:3` 的模块 docstring 就写着 `DEVELOPMENT OF THE GENERIC THERMOSTAT INTEGRATION IS FROZEN.`

**对我们的落地**：SRS FR-5.6 的"1℃ 滞回"等价于把容差设成 1.0 的双向阈值，即"室温 > 目标+1℃ 才开、< 目标−1℃ 才关"（现有 `03:333-337` 的空调状态机就是这么写的，方向正确）。但建议**同时实现一个最小切换间隔**（如 60s，正好与 `03:407` 的"60s 内不重复指令"复用同一个判据），否则 1℃ 滞回在空调这种慢惯性场景里仍然会出现分钟级抖动。**1℃ 这个数字不是国标要求**，是控制工程经验值，文档里要这么写。

### 3.5 24–28℃ / 18–22℃ 的标准出处（以及一个口径问题）

**GB 50736-2012《民用建筑供暖通风与空气调节设计规范》§3.0.2 表 3.0.2「人员长期逗留区域空调室内设计参数」**：

| 类别 | 热舒适度等级 | 温度（℃） | 相对湿度（%） | 风速（m/s） |
| --- | --- | --- | --- | --- |
| 供热工况 | Ⅰ 级 | 22～24 | ≥30 | ≤0.2 |
| 供热工况 | Ⅱ 级 | **18～22** | — | ≤0.2 |
| 供冷工况 | Ⅰ 级 | 24～26 | 40～60 | ≤0.25 |
| 供冷工况 | Ⅱ 级 | **26～28** | ≤70 | ≤0.3 |

注：Ⅰ 级热舒适度较高、Ⅱ 级一般；等级划分按 §3.0.4。条文说明进一步给出：供冷工况相对湿度 40%～70% 时对应舒适温度 22～28℃，据此取设计参数 24～28℃（Ⅰ 级 24～26、Ⅱ 级 26～28）；供热工况 Ⅰ 级 22～24、Ⅱ 级 18～22。

**口径问题（这条会影响答辩）**：指导书的"夏 24–28℃"= GB 供冷工况 **Ⅰ+Ⅱ 级全区间**；"冬 18–22℃"= GB 供热工况 **仅 Ⅱ 级**区间。两个数字来自同一张表的不同行，但一个是全区间、一个是子区间。写成"按国标设置 24–28 / 18–22"技术上不算错，但经不起细问（"为什么夏天用 Ⅱ 级、冬天用 Ⅱ 级却不含 22～24？"）。

**更稳的表述**：把 24–28 / 18–22 定义为**本系统的设定值约束区间**，依据是"GB 50736-2012 表 3.0.2 的供冷/供热室内设计参数区间"。再补一句"本标准是**设计规范**，给的是设计参数，本系统把它转用作运行期设定值上限/下限约束"——主动说明这次转用，比被问出来强。

**ISO 7730 只能给方法，给不了这两个数**：`https://www.iso.org/standard/85803.html`（ISO 7730:2025，edition 4，2025-09 发布）的官方摘要原文是"presents methods for predicting the general thermal sensation and degree of discomfort ... using calculation of predicted mean vote (PMV) and predicted percentage of dissatisfied (PPD) ... giving the environmental conditions considered acceptable for general thermal comfort as well as those representing local discomfort"。摘要里**没有任何温度数字**。附带事实：`ISO 7730:2005` 已于 2025-09-05 撤销（`https://www.iso.org/standard/39155.html`，状态 Withdrawn，被 2025 版替代）——如果论文引用 ISO 7730，要引 2025 版。

**ASHRAE 55 未能核实**：`https://www.ashrae.org/technical-resources/bookstore/standard-55-thermal-comfort` 在本环境返回 403（Cloudflare 挑战页），拿不到其条文号或图表号。见 §6。

### 3.6 手动接管让位：能借什么、必须自研什么

**HA core 里只有"归因"，没有"让位"**。`homeassistant/core.py:1344-1360`：

```python
class Context:
    """The context that triggered something."""
    __slots__ = ("_cache", "id", "origin_event", "parent_id", "user_id")
    def __init__(self, user_id=None, parent_id=None, id=None):
        ...
```

`user_id` 回答"谁触发的"、`parent_id` 串起"哪次自动化/脚本引出的"——这是**归因**，不是"暂停自动策略 30 分钟"。

**最接近的成熟实现是 custom integration**：`basnijholt/adaptive-lighting` 的 README 有一组直接对应我们 FR-5.9 的参数：

- `take_over_control`：检测到手动改动就"接管"，暂停自适应，把控制权交还给人；
- `take_over_control_mode`：`pause_all`（整灯暂停）vs `pause_changed`（只暂停被改的那个属性）——**对应我们"某设备某能力"的粒度**；
- `autoreset_control_seconds`：N 秒后自动解除接管（0 = 关闭）——**对应我们的 30 分钟窗口**；
- `detect_non_ha_changes`：识别"不是通过 HA 改的"状态变化（外部遥控器/物理开关）；
- `adapt_only_on_bare_turn_on`：场景/集成的整体开启**不**被标记为手动——**对应我们"场景执行解除让位"的反向问题**。

**结论：自研，但照这个参数表设计。** 我们的判据更简单（ADR 0002:96 已定：靠 `command_log.source='manual'`，不靠 `user_id`），实现上可以完全不加列：

1. `lastManualAt(item, capability)` = `command_log` 里该 `(item_id, capability_key)` 最近一条 `source='manual'` 的 `created_at`（聚合查询，不需要新列）；
2. 抑制条件：`now - lastManualAt < 30min` **且** 没有被解除；
3. 解除条件：① 期间出现新的 `source='manual'` 命令（时间戳自然前移）；② 该设备该能力参与了一次场景执行（`run` 的 `started_at` 晚于 `lastManualAt`）；③ 读数相对**手动时刻的基线**超阈值（温度 ±3℃ / 湿度 ±10%RH / 光照 ±200lux）。

**缺口**：条件 ③ 需要"手动时刻的读数基线"。`command_log` 只存命令，不存当时的温度/湿度/光照（已核 `sql/0001_init.sql` 无相关列）；`state_history` 能倒查，但要在执行期每分钟做一次三表 join + 回查，代价与"内存里存一份基线"不是一个量级。→ **必须新增一样东西**（进程内 map 或一张 `manual_override` 小表），`docs/notes/02-Home-Assistant-参考.md:135` 当年提的 `suppressed_until` 字段方向是对的，只是它不够——还需要 `baseline_reading`。这是 §4 里判为"冲突"的那个条目。

**另一个顺序问题**：`03:317` 写"先打手动接管标记再下发"，而 FR-5.9 要求"有场景执行则立即解除让位"。场景执行时若沿用"先打标记"，用户的自动场景会被自己的手动标记挡掉。正确顺序应是：**场景 run 开始时先清该 run 涉及设备/能力的让位标记，再下发**；手动命令才走"先标记再下发"。这条目前没有任何文档写。

### 5.1 分层（与现有模块划分对齐，不新增层）

### 5.2 明确取舍（"别造轮子"清单）

1. **照抄 HA 的语义与命名**：`mode` 四值、`max`/`max_exceeded`、`continueOnError`、`enabled`、`alias`、步级 `timeout`。这些词在 HA 文档里有出处，答辩时一句"对齐 Home Assistant 的 script 模型"就能解释，比自己发明"重试策略/跳过开关"强。
2. **不照抄 HA 的实现**：asyncio 协程树、`_ScriptRun` 类层级、trace 文件。我们要的是**顺序 + 可查执行记录**，Go 里一个栈循环 + 两张表更短。
3. **不引入 CEL、不引入 gocron**；**引入 jsonschema v6** 校验 `definition`（并在 `openapi.yaml` 里定义 schema，服务端与前端共用同一份）；`errgroup` 留给将来的 `parallel`。
4. **守卫只做一套**：结构化 `{all|any:[{itemId,capability,op,value}]}`，与 seed 现存格式一致（`sql/seed.sql:111`），别一边顶层 guard、一边 choose 里再放一套不同结构的条件。
5. **让位状态不落新列也能做**（聚合 `command_log`），但**基线读数必须存**——存内存 map 即可（单实例），并在重启后按"无基线=不放行"处理（`CONTEXT.md:65` 的状态过期哲学：宁可显示不知道）。
6. **进度只有一个来源**：`run_step`。前端不要缓存"执行到第几步"，一切来自 WS `run_step`（`04:291`）；断线重连后拉 `GET /api/runs/{id}` 重建。

### 5.3 落地顺序（最小可验收路径）

1. 契约：5 个 schema + 4 个端点（`openapi.yaml`）→ 生成物替换。
2. seed：补齐 3（或 5）个模式，`回家` 的空调动作改 `valueFrom:"comfort"`。
3. `ModeRunner.Start` + `Advance`：先只支持 `action`/`delay`，跑通"开灯 → 等 2s → 调亮度 → 时间线点亮"。
4. `choose` + 结构化守卫。
5. `policy/comfort.go` + 依据文案；`policy/yield.go` + 30 分钟窗口。
6. 异常三件套：离线（该步 failed + 继续/中止）、5 分钟超时（skipped 剩余）、重复触发（restart 默认）。
