# ADR 0002 · 数据模型与分层

> 状态：**草案 · 暂缓评审**（2026-11-20：本文件写在第 10 周需求分析之前，属提前决策，暂不作为设计依据）

> 日期：2026-11-20
> 依据：[`docs/04-架构借鉴清单.md`](../04-架构借鉴清单.md)（扩展点取舍与 HA 的四笔债）、[`docs/00-指导书调研.md`](../00-指导书调研.md)（F1–F5 / E1–E4 判据）、[`ADR 0001`](0001-技术栈选型.md)（技术栈与分层落点）。
> 本文只定**数据模型**与**层间接缝**；具体 DDL 在 `sql/` 迁移里，接口签名在 `openapi.yaml` 与 Go 代码里。

## 1. 背景

指导书 3.4 把数据模型定成三层：**类型 → 能力 → 状态**。类型描述「这是什么」（灯、空调、沙发）；能力描述「单个可读写属性的元数据」（亮度、色温）；状态描述「当前值」。

三条硬约束决定了这份设计的形状：

1. **F2 要求「新增设备类型不需改前端代码」**，故能力必须是**运行期数据**，由前端读元数据渲染表单，不能靠类型系统推导。
2. **F4 要求「状态在平面图、设备列表、控制面板三处一致」**，故状态只能有一个写入点、一个真相源，否则三处必然漂移。
3. **F1 要求「坐标改动必须落到数据层」**，故平面图坐标是数据库里的字段，不是前端本地状态。

本项目为 3 人、单家庭、13 台固定设备 + 1 台移动设备。这个规模是**判断任何「要不要拆表」问题的前提**：HA 的三层 registry、config entry、recorder 是为多集成 / 千万用户 / 十年升级付的税，我们不共享那个前提（论证见 `docs/04` §2.3、§4）。

## 2. 决策

### 2.1 表清单

| 表 | 作用 | 主键 |
| --- | --- | --- |
| `room` | 房间；`polygon` jsonb 存轮廓 | `id` uuid |
| `wall` | 墙体线段（F3 画墙），两端坐标 + 厚度 + 高度 | `id` uuid |
| `item_type` | 类型模板，`kind ∈ {furniture, device}`；`capabilities` jsonb 存能力元数据 | `id` uuid，`key` 唯一 |
| `item` | 全部物品与设备（家具与设备同表） | `id` uuid |
| `capability_state` | 每个数据点的当前值与来源 | `(item_id, capability_key)` |
| `state_history` | 状态变化日志（只存变化） | `id` bigserial |
| `command_log` | 命令尝试日志（含失败与超时） | `id` bigserial |
| `app_user` | 家人账号与角色（`admin` / `member`） | `id` uuid |
| `mode` / `run` / `run_step` | F5 场景编排、执行、步骤回显 | `id` / `id` / `(run_id, node_id)` |

**家具与设备同表**：二者在平面图里都是矩形、都有房间与坐标，唯一实质差别是「有没有 capability」。拆两张表会让 F1 的「全部物品与设备的 CRUD + 筛选 + 导入导出」三件事全部翻倍（UNION、两套导出结构、合并排序分页），也会让 F2 变成两套类型管理界面。佐证：HA 允许「有 device 而无 entity」（hub 类设备），家具等价于零能力的设备。

### 2.2 键与类型

- **`item` 用 uuid v4**（PG17 内置 `gen_random_uuid()`）。理由不是性能，是**身份键的稳定性**：UUID 让「导出 JSON → 另一台机器导入」不撞号，也让将来加 `tenant_id` 时不需要重建约束。HA 两笔债（device 全局唯一标识、`restore_state` 按 `entity_id` 索引）都是「身份键选了可变或可复用的东西」（`docs/04` §4.1）。
- **日志表用 bigserial**：纯追加、体量大、只被聚合查询读，bigint 更小更快。
- **`item` 删除后 id 不复用。**
- **所有时间列用 `timestamptz`**：否则后端容器 UTC、前端 Asia/Shanghai、换机器演示会各差 8 小时，而 F4 的「最近更新时间」要显示给人看。
- **`capability_key` 发布后不得重命名**；改名走「新增 key + 迁移 + 保留旧 key 一个迭代」。
- **`item.status` 只对 `kind='furniture'` 有语义**（正常 / 闲置 / 维修）。设备不读该列，设备状态一律在 `capability_state`——这是为了避免 F1 要求的「状态」字段变成第二份真相。

### 2.3 能力元数据的格式

`item_type.capabilities` 是一个数组，每项：

```jsonc
{
  "key": "brightness",          // 稳定标识，发布后不改名
  "name": "亮度",
  "type": "number",             // bool | number | enum | string
  "unit": "%",
  "min": 0, "max": 100, "step": 1,
  "options": [{ "value": "cool", "label": "制冷" }],  // type=enum 时使用
  "writable": true,
  "default": 0,
  "history": true,              // 是否写 state_history
  "icons": { "off": "bulb-off", "on": "bulb-on" }     // 选填，F3 图标
}

```

另有 `item_type.capabilities_version`（整数）：改结构时据此判读旧数据。

**这份元数据同时是**：前端动态表单的字段描述（F2）、后端命令校验的规则来源、模拟器的行为描述、平面图图标的映射表。同一个结构服务四处，这是本项目「一次定义、四处分发」的核心。

### 2.4 单一写入点

状态只有一条写入路径，其他任何地方都不得直接写 `capability_state`：

```
前端 (HTTP) ──► control.Execute(cmd) ──► device.Adapter ──► 读回设备值
                     │                                        │
                     └────────── store.WriteState ────────────┘
                                      │
                                      ├─► capability_state (upsert)
                                      ├─► state_history    (值或 source 变化时追加)
                                      ├─► command_log      (成功/失败/超时都记)
                                      └─► broadcaster.Broadcast ──► /ws/state
```

四条不变量：

1. **广播出去的值一定是落库后的值**，不是命令里的期望值，也不是设备回包的原始字节。
2. **失败的命令也写 `command_log`**，但不写 `state_history`（值没变）。只靠状态变化永远补不出「谁在什么时候试过、为什么失败」。
3. **`source ∈ {manual, automation, device, timeout}`**：E1 的「手动接管后自动策略让位」靠它判定，不靠 `user_id`。
4. **`capability_state.updated_at` 就是 F4 的「最近更新时间」**，是必填列不是装饰；超出窗口未更新即标 `unavailable`，绝不显示过期值（`docs/04` §2.1 第 2 条）。

### 2.5 接缝清单

「可扩展」在本项目里被定义为**可加不可改 + 有接缝 + 可一次性重建**，不是「预留所有未来字段」（论证见 `docs/04` §4.3）。接缝清单如下，**新增能力只能在边界内侧实现，不得新增边界**：

| # | 接缝 | 现在怎么做 | 将来怎么接 | 触发条件 |
| --- | --- | --- | --- | --- |
| S1 | **多租户** | 不建 `tenant_id`；所有数据访问经 `backend/store` 一层，不裸露 SQL；主键全局唯一 UUID | `ALTER TABLE … ADD COLUMN tenant_id uuid NOT NULL DEFAULT '<默认租户>'` + 在 store 层统一加过滤条件；无需重建任何唯一约束或外键 | 真的出现第二个家庭/组织 |
| S2 | **真实硬件（Matter / HTTP）** | `device.Adapter` 接口 + 模拟器实现；`item_type` 上留 `driver` 字段标明该类型由哪个 adapter 供给 | 新增一个 adapter 实现并注册，不动控制层与展示层 | 拿到能联调的硬件 |
| S3 | **桌面壳（mygo）** | 前端只依赖 HTTP + WS，不假设浏览器专有 API；构建产物是静态站点 | mygo webview 直接加载同一份构建产物，后端仍是同一个 Go 进程 | 主线闭环之后（第二阶段） |
| S4 | **三维视口** | 2D 数据即模型：`x/y/rotation` + `item_type.default_size`；3D 只做投影，不另建数据结构 | 需要材质/模型时，往 `item.attrs` 与 `item_type` 里加字段，不改表结构 | 3D 视口开发时 |
| S5 | **长时统计** | `state_history` 加 `(item_id, capability_key, recorded_at DESC)` 索引 | 建按小时的物化视图；写入路径完全不用改 | 历史数据量增长到需要聚合 |
| S6 | **场景快照** | 不建表；F5 走脚本语义（有序步骤），不是状态快照 | 快照 = 一组 `(item_id, capability_key, value)`，与 `capability_state` 同构，随时可加表 | 需要「恢复到我离开前的样子」 |
| S7 | **权限细化** | `app_user.role ∈ {admin, member}` + 各写操作的 `created_by` | 加角色表或策略字段；已有的 `created_by` 是审计与判权的基础 | 角色超过两种 |

**接缝总数的自检**：跨层边界只有四个接口——展示层 → 控制层（OpenAPI/WS 契约）、控制层 → 策略层（`Policy`）、控制层 → 设备层（`Adapter`）、控制层 → 数据层（`Store`），外加一个出站方向（`Broadcaster`）。**接口声明数超过 5 个就是过度设计**（`docs/04` §4.3 的检查方法）。

### 2.6 分层落点

| 层 | 目录 | 职责 | 不得做的事 |
| --- | --- | --- | --- |
| 展示层 | `frontend/src/` | 渲染、交互、表单、平面图与 3D | 不得直接调设备；不得自己算舒适温度 |
| 策略层 | `backend/policy/` | 纯函数：给定环境与目标，返回「目标值 + 依据字符串」 | 不得访问数据库或网络 |
| 控制层 | `backend/control/` | 唯一的写入点；命令分发、校验、状态回写、广播 | 不得绕过 store 直接执行 SQL |
| 设备层 | `backend/device/` | `Adapter` 接口与模拟器实现 | 不得知道 HTTP 或 UI 的存在 |
| 数据层 | `backend/store/` + `sql/` | 查询与事务；sqlc 生成的代码也在这层内 | 不得包含业务判断 |

依赖方向单向向下，**不允许反向 import**。展示层与后端之间只有 `openapi.yaml` 是与代码同源的契约。

### 2.7 迁移与重建

- 迁移只做**加表 / 加列（带默认值）/ 加索引**；重命名与删除进负债清单并留一个迭代。
- 每个迁移文件只有一个目的。
- 只保证最近一步的 `down` 可用。
- **`migrate down → up → seed` 能在十秒内重建全部演示数据**（13 台设备、平面图、5 个场景模板），`seed.sql` 里的 UUID 写死，保证重建确定。这条比任何预留字段都值钱：课程设计里 schema 改三次是常态，真正贵的不是改，是改完老数据对不上。
- sqlc 的 `jsonb` 默认映射为 `[]byte`（nullable 与非 nullable 都是），故在 `sqlc.yaml` 里用 `overrides[].go_type` 统一定成 `json.RawMessage`，否则每个 handler 都要手写反序列化。**必须写两条规则**：一条 `db_type: jsonb`，一条带 `nullable: true` 的同款规则——少写后者时，nullable 列（如 `command_log.target`）会静默退回 `[]byte`（V5 实测）。

### 2.8 认证与权限（第一批就做）

鉴权一旦缺席，第一版 `openapi.yaml` 和所有 handler 签名在后期都要整体改一遍；而它本身只是「一个中间件 + 一张表 + 一个登录页」。故 `app_user` 与鉴权中间件排进第一批，不后补。

- **账号体系**：2–4 个家人账号（指导书 2.3 只要求「单用户口令或简单账号体系即可」，多用户与权限属鼓励做，我们按账号体系实现）。
- **会话方式**：`httpOnly` + `SameSite=Lax` 的会话 Cookie，服务端存会话；不用 `localStorage` 里的 Bearer token——XSS 即失窃。
- **WebSocket 复用同一个 Cookie**：浏览器在同源 WS 握手时会带上 Cookie，`/ws/state` 不需要另设一套 token 机制，也就不会出现「HTTP 已登录、WS 未认证」的裂缝。
- **CSRF**：变更类请求要求自定义头 `X-Requested-With`（跨站表单带不了自定义头），配合 `SameSite=Lax` 足够；不引 CSRF token 框架。
- **角色**：`admin` 管配置（类型、设备、房间、用户、导入导出），`member` 管操作（控制设备、执行与编辑场景、查看状态与历史）。
- **契约**：`openapi.yaml` 的 `securitySchemes` 从 v1 就声明 Cookie 认证并全局生效，登录与健康检查用 `security: []` 例外——**这样接口签名只需要定一次**。
- **留痕**：所有写操作带 `created_by`（`command_log`、`mode`、`item`），它同时是 S7 的接缝基础。

## 3. 否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 拆 device / entity 两张表（照搬 HA） | 我们只有一个供给方（模拟器），「集成上报 vs 用户改动」两份数据从不同时存在，registry 分层没有作用点；抄过来只会多出一张永远与 `item_type` 打架的表（`docs/04` §2.3） |
| 状态整块存 `item.state` jsonb | F4 的「最近更新时间」必须**按数据点**记：13 台设备里 6 台可写、7 台只读上报，共用一个 `updated_at` 会让传感器上报刷新「设备被操作」的时间戳。且 WS 行级推 `{itemId, key, value, ts}` 直接 setState，整块 jsonb 要自己写 diff |
| capability 单独建字典表 | 65 行数据，真要拆是一小时脚本；建表还会立刻制造二次真相（jsonb 一份、表里一份）。能力是「描述的元数据」，不是实体（指导书 3.4 原话） |
| 通用 EAV 属性表 | 类型全丢、导入导出要重建结构、前端要猜类型；从 EAV 回到强类型列是灾难级迁移 |
| `state_history` 按时间分区 | PG17 要求分区表的唯一约束必须包含全部分区键列，主键得变成 `(id, recorded_at)`，还要分区维护任务；三周约 180 万行，单表无压力 |
| 内存状态机 + 异步落库 | 迭代期一天重启十几次，重启后平面图全灰；且会产生两个「当前状态」，直接顶掉 F4「三处一致」这个核心验收点 |
| 软删除 `deleted_at` | 每条查询都要带 `WHERE deleted_at IS NULL`，漏一处就是幽灵数据；`state_history` 本身已保留历史 |

## 4. 后果

**正面**

- 13 台设备 + 家具共用一套表，F1 的 CRUD / 筛选 / 导入导出只实现一遍。
- 新增一个设备类型 = 插一行 `item_type`，前端零改动（F2 的验收题）。
- 状态只有一个写入点，F4 的「三处一致」是结构性保证，不是靠测试兜底。
- 鉴权从第一版契约就在场，接口签名不需要在后期整体改一遍；`created_by` 顺带把审计与权限留痕一并解决。
- 多租户、真实硬件、桌面壳、三维、统计、快照、细粒度权限都留了接缝，且都不需要现在建表。

**负面 / 风险**

- `capability_state` 比「整块 jsonb」多一次 join / upsert，量级是 13 台 × 约 5 个数据点 ≈ 65 行，可忽略。
- `item` + `item_type` + `capability_state` 三张表意味着 F1 的列表查询要 join 两次；查询语句由 sqlc 生成，维护成本可控。
- 接缝存在不等于实现便宜：S2（真实硬件）与 S6（快照）都是「接得上但要写」，评估工作量时不能把接缝当作已完成。
- `capability_key` 的稳定性是一条**纪律而非技术约束**，没有数据库层面的强制；靠 review 与 ADR 保证。

## 5. 待验证

> 这四条的判定口径与退路已合并进 [`docs/05-技术验证清单.md`](../05-技术验证清单.md) 的 V5–V8。

1. 已验证——sqlc 的 `jsonb` override 能让「参数」与「扫描结果」同时生效；nullable 列需额外一条 `nullable: true` 的规则（V5 实测，证据见 [docs/05](../05-技术验证清单.md)）。
2. 已验证——`command_log` 与 `state_history` 能在同一 `pgx.Tx` 内一起提交/回滚（V6 实测）。
3. 待复核——13 台设备的 capability 实际数量与变化频率——V7 推演约 45 行、单类型最多 6 条，写 `seed.sql` 时按实际清单复核。
4. 待验证——两种角色是否够用：`admin` / `member` 之外若出现「只能看不能控」的访客，S7 会提前触发。留到第 10 周用例后评审（V8）。

| # | 复核项 | 为什么可能变 | 复核方法 |
