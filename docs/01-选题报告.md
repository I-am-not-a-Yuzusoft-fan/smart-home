# 选题报告 · 智能家居系统

> 第 9 周交付物（指导书 [1.3](<../课程设计书/2026智能家居系统-课程设计指导书.md>) 进度表）。对应「场景设定、同类产品调研、技术选型、分工」四项关键任务。
> 状态：**草稿**。家庭白描待组内确认；分工表已按 3 人组定稿，待填姓名。

## 1. 选题与定位

用一个**真实可感的家庭**当需求起点，做一个浏览器里能用的智能家居控制系统：建户型 → 摆家具与设备 → 控制设备 → 看状态 → 一键场景。

不做「大而全的 IoT 平台」，做**一个家庭的一周**。差异点在三处：

1. **平面图与 3D 同源**：同一份设计数据投影出 2D 编辑视图与 3D 鸟瞰，改一处两处都变。
2. **温度不是写死的**：舒适度按季节、室内外温湿度计算，带 1℃ 滞回，并说明调节依据。
3. **管家能解释**：「为什么现在开空调」有答案，不是黑箱。

## 2. 场景设定

### 2.1 家庭

| 项 | 内容 |
| --- | --- |
| 房屋 | 89㎡ 三室两厅一卫，南京，南向客厅 + 主卧 + 次卧 + 书房 |
| 成员 | 张先生 32 岁，程序员，每周两天居家办公；李女士 30 岁，护士，三班倒；女儿 5 岁，次卧；张母 62 岁，怕冷，有高血压，睡书房 |
| 经济 | 双职工，愿意为「省心」付费，不愿意为「参数」付费 |

### 2.2 一周里的五个真实痛点

1. **三班倒的作息**：李女士有时凌晨 3 点回家，有时 6 点出门。固定的「睡眠模式」时间表对她无效。
2. **老人起夜**：张母夜里 2 点起夜，需要走廊一盏不刺眼的小夜灯；她怕冷，冬天房间不能低于 20℃。
3. **白天无人空转**：张先生居家的日子和上班的日子不一样，空调常常开一整天没人。出门忘关灯是常态。
4. **孩子房间**：5 岁女儿睡觉踢被子，房间不能太干（加湿器要自动）。
5. **回家那 30 秒**：抱着一堆东西进门，要摸黑找开关、开空调、拉窗帘、开净化器。

### 2.3 设备清单（决定 F1/F2 的类型库规模）

| 类别 | 具体设备 | 能力（决定 F2 的差异化属性） |
| --- | --- | --- |
| 灯 | 客厅主灯、走廊夜灯、卧室吸顶灯 | 开关、亮度 0–100、色温 2700–6500K |
| 空调 | 客厅柜机、主卧挂机、次卧挂机 | 开关、模式、目标温度 16–30℃、风速 |
| 窗帘 | 客厅、主卧 | 开合度 0–100% |
| 环境电器 | 加湿器、空气净化器 | 开关、档位 |
| 传感器 | 温湿度 ×3、人体存在 ×3、门磁 ×1 | 只读，按周期上报 |
| 移动设备 | 扫地机器人（选做 E2） | 位置、朝向、电量、工作状态 |

合计 13 个固定设备 + 1 个移动设备，跨 6 个类别——足以撑起 F2「新增类型不改前端」的验证。

### 2.4 场景（决定 F5 与 E1）

| 场景 | 触发 | 动作集 |
| --- | --- | --- |
| 回家 | 门磁开启 + 人体检测到入户 | 玄关灯 30% → 客厅灯 80% → 空调（按季节算温）→ 窗帘 70% → 净化器 1 档，带 2s 间隔 |
| 离家 | 门磁关闭 + 10 分钟无人 | 全灯关 → 空调关 → 窗帘全闭 → 净化器关 |
| 睡眠 | 手动 / 22:30 后主卧无人移动 5 分钟 | 全屋灯关（走廊留 5% 夜灯）→ 空调切睡眠曲线 |
| 夜起（E1） | 走廊人体传感器 | 夜灯 8%、2700K，3 分钟后自动关 |
| 补眠（三班倒） | 手动一键 | 全屋静音、拉窗帘、空调维持 24℃ |

## 3. 功能边界

**必须做（F1–F5，缺项直接掉分）**

- F1 家居物品管理：增删改查、按房间/类别筛选、关键字搜索、JSON 导入导出、坐标落库
- F2 家具库：类型模板 + 差异化属性 + 示意图；**新增类型不改前端代码**（数据驱动动态表单）
- F3 平面图：画墙（网格吸附 + 端点捕捉）、拖拽/旋转/删除、选中改属性、持久化
- F4 控制与状态：下发命令、三处状态一致（平面图/列表/面板）、当前值 + 更新时间 + 历史曲线、成功/失败/超时反馈、模拟器
- F5 一键策略：**通用步骤编辑器**（增删步骤、`choose`/`delay` 嵌套、拖拽排序），内置回家/离家/睡眠/夜起/补眠 5 个模式作为模板；条件 + 动作集（带参数与延时）；**温度动态计算 + 1℃ 滞回 + 依据文案**；执行过程按步骤回显状态

**选做（指导书 2.2，本组全做，按此优先级砍）**

| 编号 | 内容 | 本组取舍 |
| --- | --- | --- |
| E1 | 房间环境感知与自适应（多目标冲突 + 手动接管） | 做。它是 F5 的自然延伸，且「手动接管后策略让位」是很好的答辩点 |
| E2 | 可移动设备（扫地机器人 + 栅格 A* 路径） | 做。与 F3 平面图共用栅格，边际成本低；**第二个砍** |
| E3 | 自然语言控制（四元组 + 降级关键词 + 危险操作确认） | 做。云端 API + 关键词降级；**最后一个砍** |
| E4 | 智能管家（多轮 + 偏好记忆 + 习惯挖掘 + 解释） | 做，但只做「偏好记忆 + 解释」，不做完整多轮；**先砍** |

**不做 / 不允许**

- 不做真实硬件对接（指导书允许模拟器）
- 不做用户体系与多租户（单家庭，无登录）
- 不允许套用现成平台换皮；不允许只写文档不写代码

## 4. 同类产品调研

| 产品 | 形态 | 与本题的关系 |
| --- | --- | --- |
| [Home3D (lohith9/Home_View)](https://github.com/lohith9/Home_View) | 前端纯 2D/3D 户型设计器，React + Canvas + three | 指导书第 4 章的推荐复用对象。**已核验：仓库无许可证**，且 4120 行前端零 TypeScript、无 API 层。结论：只借鉴其「同一份设计数据双投影」的范式，不复制代码 |
| [react-planner](https://github.com/cvdlab/react-planner) | 2D/3D 户型规划，MIT | 许可证干净的可选参考；但 2024-04 后未更新，依赖老旧 |
| [Home Assistant](https://github.com/home-assistant/core) | 开源自动化平台（Apache-2.0），YAML 配置 | **重点参考对象**：其「场景 / 脚本 / 自动化」三分法与 target 寻址直接决定我们 F5 的数据模型。已专门核验，见 [`docs/02-Home-Assistant-参考.md`](02-Home-Assistant-参考.md) |
| 米家 / Apple 家庭 | 商业 App | 交互与场景命名的参照；封闭，不可复用 |

**本组的差异**：上面这些要么只会画图（Home3D/react-planner），要么只会控制（Home Assistant），要么封闭（米家）。本题要求的是**画完图能直接控**，这正是要做的缝合。

Home Assistant 的参考结论（详见 [`02-Home-Assistant-参考.md`](02-Home-Assistant-参考.md)）：借鉴它的**设计契约**（三分法、区域寻址、run mode、单步启用/失败策略、场景快照），不借鉴它的**实现形态**（YAML 优先、Python asyncio、Jinja 模板、Blueprint）。它管不到的部分——按季节与室内外温湿度动态算温、1℃ 滞回、附调节依据——恰好是指导书 F5 的评分区分点，由我们自己实现。

## 5. 技术选型

一句话：**React 19 + TypeScript + three.js 自研前端；Go + PostgreSQL 后端；OpenAPI 契约先行；mygo 桌面壳作为可选加分项。**

完整理由、被否决的方案、以及第 1 周要跑的 4 项验证见 [`docs/adr/0001-技术栈选型.md`](adr/0001-技术栈选型.md)。指导书 3.3 要求「可替换但需在设计文档说明理由」，该 ADR 就是那份理由。

## 6. 分工表

> **3 人组**，设组长 1 名。按「三条纵切轨」分工，每条轨从上到下贯穿五层，避免按层切导致的互相等待。三条轨的边界由 OpenAPI 契约界定，A 轨是唯一的契约修改入口。

| 轨 | 成员 | 职责 | 主要交付 | 主要周次 |
| --- | --- | --- | --- | --- |
| **A 数据与契约**<br>（组长） | 待填 | 表结构与迁移、OpenAPI 契约、F1 物品管理（CRUD / 搜索 / 筛选 / 导入导出）、seed 数据、E3 后端接入与关键词降级 | `sql/` 迁移、`backend/store/`、`backend/api/`、`openapi.yaml` | 12 建表与 CRUD；13 导入导出；14 测试报告与性能数据 |
| **B 前端与建模** | 待填 | 前端脚手架、F2 类型模板驱动的动态表单、F3 平面图、F5 步骤编辑器界面、主题层与看板娘 | 「新增类型不改前端」的实证、可建图、可编辑场景 | 12 建图 + 类型模板；13 控制面板 + 编辑器；14 主题与 3D 增量 |
| **C 运行时与策略** | 待填 | 设备模拟器、F4 命令 / 状态 / 历史 / WS 推送、F5 执行引擎、E1 环境自适应、E2 栅格路径规划 | 三处一致、场景可执行 | 12 薄链路；13 全设备状态同步；14 策略与 E1 |

组长兼任 A 轨，是因为契约是三条轨唯一共享的东西——谁改契约谁就要对所有下游负责。若组长更擅长前端，可与 B 轨互换，但**契约守门人必须是同一个人**，不能两人共管。

三人组下选做功能的取舍：**E1、E2、E3 保留，E4 放弃**（E4 的完整多轮对话在三人组里性价比最低；若第 14 周有余力，降级为「偏好记忆 + 一句解释」，挂在 A 轨）。

### 协作方式

采用**迭代增量交付**：三个迭代，每个迭代末产出可运行版本并附测试报告；任务用 GitHub Issues 看板管理；每周一次集成与代码互评。

| 节奏 | 动作 | 对应要求 |
| --- | --- | --- |
| 周一 15 分钟 | 站会：上周合了什么、本周合什么、卡在哪（写进 Issue 评论，不单独留纪要） | — |
| 周四 | 集成日：全员合入 `main`，跑通 `start.sh` | 指导书 5.3「每周至少一次完整合并与联调」 |
| 周五 | 每人 review 他人至少一个 PR，记录落 `docs/reviews/` | 指导书 1.3「至少每周一次代码互评，记录计入过程考核」 |
| 迭代末 | 打 tag `v0.1` / `v0.2` / `v0.3`，附测试报告 | 指导书进度表「可交付版本」 |

**第 12 周前 3 天先出 walking skeleton**：由 A 轨一人搭出一条端到端链路（一张表 + `GET /api/items` + `POST /api/items/{id}/commands` + 一条 `/ws/state` 推送 + 一个开关按钮 + 一个改内存的模拟器），合入 `main` 后全组从它开分支。它不是 MVP——只求「通了」，不求「能用」，工期硬性 3 天封顶。

指导书 1.3 要求：**不得有只写文档不写代码的成员**；故上表三人均有代码产出，评审记录落 `docs/reviews/`。
