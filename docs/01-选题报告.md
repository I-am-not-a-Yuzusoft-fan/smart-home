# 选题报告 · 智能家居系统

> 第 9 周交付物（指导书 [1.3](<../课程设计书/2026智能家居系统-课程设计指导书.md>) 进度表）。对应「场景设定、同类产品调研、技术选型、分工」四项关键任务。
> 状态：**草稿**。家庭白描待组内确认；分工表已按 3 人组定稿，待填姓名。

## 1. 选题与定位

用一个**真实可感的家庭**当需求起点，做一个浏览器里能用的智能家居控制系统：建户型 → 摆家具与设备 → 控制设备 → 看状态 → 一键场景。

不做「大而全的 IoT 平台」，做**一个家庭的一周**。差异点在三处：

1. **平面图与 3D 同源**：同一份设计数据投影出 2D 编辑视图与 3D 鸟瞰，改一处两处都变。
2. **温度不是写死的**：舒适度按季节、室内外温湿度计算，带 1℃ 滞回，并说明调节依据。
3. **管家能解释**：「为什么现在开空调」有答案，不是黑箱。

## 2. 场景设定

### 2.1 家庭

| 项 | 内容 |
| --- | --- |
| 房屋 | 89㎡ 三室两厅一卫，南京，南向客厅 + 主卧 + 次卧 + 书房 |
| 经济 | 双职工，愿意为「省心」付费，不愿意为「参数」付费 |

**成员与账号**（多用户与权限的落点）：

| 成员 | 画像 | 账号 / 角色 |
| --- | --- | --- |
| 张先生 | 32 岁，程序员，每周两天居家办公 | `admin`：管类型、房间、账号、导入导出 |
| 李女士 | 30 岁，护士，三班倒 | `member`：控制设备、执行与编辑场景 |
| 张母 | 62 岁，怕冷，有高血压，夜里起夜，睡书房 | `member`：只用大按钮控制灯与空调，不改配置 |
| 女儿 | 5 岁，次卧 | 无账号 |

四种人只需要两种角色，因为权限差异只出现在「改配置还是只操作」这一条线上。它落在两处数据上：`command_log.created_by`（谁下发的命令）与 `mode.created_by`（谁建的场景）。E1 的「手动接管后自动策略让位」判定的是**动作来源**（`capability_state.source = manual`），不是谁点的——身份只用于事后追溯，这样判定逻辑不会因为多一个家人而变形。

### 2.2 一周里的五个真实痛点

1. **三班倒的作息**：李女士有时凌晨 3 点回家，有时 6 点出门。固定的「睡眠模式」时间表对她无效。
2. **老人起夜**：张母夜里 2 点起夜，需要走廊一盏不刺眼的小夜灯；她怕冷，冬天房间不能低于 20℃。
3. **白天无人空转**：张先生居家的日子和上班的日子不一样，空调常常开一整天没人。出门忘关灯是常态。
4. **孩子房间**：5 岁女儿睡觉踢被子，房间不能太干（加湿器要自动）。
5. **回家那 30 秒**：抱着一堆东西进门，要摸黑找开关、开空调、拉窗帘、开净化器。

### 2.3 设备清单（决定 F1/F2 的类型库规模）

| 类别 | 具体设备 | 能力（决定 F2 的差异化属性） |
| --- | --- | --- |
| 灯 | 客厅主灯、走廊夜灯、卧室吸顶灯 | 开关、亮度 0–100、色温 2700–6500K |
| 空调 | 客厅柜机、主卧挂机、次卧挂机 | 开关、模式、目标温度 16–30℃、风速 |
| 窗帘 | 客厅、主卧 | 开合度 0–100% |
| 环境电器 | 加湿器、空气净化器 | 开关、档位 |
| 传感器 | 温湿度 ×3、人体存在 ×3、门磁 ×1、光照 ×1（客厅 0–2000 lux） | 只读，按周期上报 |
| 移动设备 | 扫地机器人（选做 E2） | 位置、朝向、电量、工作状态 |
| 真实硬件（可选） | 一台 Matter 智能灯（试点） | 开关、亮度、色温；由 `driver=matter` 的 Adapter 供给，其余设备仍走模拟器 |

合计 14 个模拟设备 + 1 个移动设备 + 1 台可选真实硬件，跨 6 个类别——足以撑起 F2「新增类型不改前端」的验证。Matter 灯不是为了叙事，是为了让 S2（真实硬件接缝）有一个能真的插上去的孔：如果 `Adapter` 只能对接模拟器，那它就只是个装饰。

光照传感器是补的缺口：指导书 E1 要求「接入或模拟温度、湿度、光照、人体存在」四条，早期清单只有温湿度与人体，缺光照。补 1 个（而不是每间房一个）是因为 E1 的自适应规则里只有「光照低于阈值自动开灯」这一条真正用得上，而它发生在客厅。

### 2.4 场景（决定 F5 与 E1）

| 场景 | 触发 | 动作集 |
| --- | --- | --- |
| 回家 | 门磁开启 + 人体检测到入户 | 玄关灯 30% → 客厅灯 80% → 空调（按季节算温）→ 窗帘 70% → 净化器 1 档，带 2s 间隔 |
| 离家 | 门磁关闭 + 10 分钟无人 | 全灯关 → 空调关 → 窗帘全闭 → 净化器关 |
| 睡眠 | 手动 / 22:30 后主卧无人移动 5 分钟 | 全屋灯关（走廊留 5% 夜灯）→ 空调切睡眠曲线 |
| 夜起（E1） | 走廊人体传感器 | 夜灯 8%、2700K，3 分钟后自动关 |
| 补眠（三班倒） | 手动一键 | 全屋静音、拉窗帘、空调维持 24℃ |

五个场景全部按**脚本语义**实现（有序步骤、可延时、有过程反馈），不是「设备 → 状态」的快照——这是 Home Assistant 的三分法给我们的结论（见 [`02-Home-Assistant-参考.md`](02-Home-Assistant-参考.md)）。场景的创建者记进 `mode.created_by`，执行产生的每条命令记进 `command_log`，于是「谁在什么时候试过什么、成没成」永远答得出来。

## 3. 功能边界

**必须做（F1–F5，缺项直接掉分）**

- F1 家居物品管理：增删改查、按房间/类别筛选、关键字搜索、JSON 导入导出、坐标落库
- F2 家具库：类型模板 + 差异化属性 + 示意图；**新增类型不改前端代码**（数据驱动动态表单）
- F3 平面图：画墙（网格吸附 + 端点捕捉）、拖拽/旋转/删除、选中改属性、持久化
- F4 控制与状态：下发命令、三处状态一致（平面图/列表/面板）、当前值 + 更新时间 + 历史曲线、成功/失败/超时反馈、模拟器
- F5 一键策略：**通用步骤编辑器**（增删步骤、`choose`/`delay` 嵌套、拖拽排序），内置回家/离家/睡眠/夜起/补眠 5 个模式作为模板；条件 + 动作集（带参数与延时）；**温度动态计算 + 1℃ 滞回 + 依据文案**；执行过程按步骤回显状态

**选做（指导书 2.2）：四项全部纳入范围**

| 编号 | 内容 | 落地方式 |
| --- | --- | --- |
| E1 | 房间环境感知与自适应 | 完整实现：温湿度/光照/人体多目标冲突决策规则 + 手动接管后策略让位 |
| E2 | 可移动设备 | 完整实现：位置、朝向、电量、工作状态；平面图实时位置与轨迹；栅格地图 + A* 覆盖路径 |
| E3 | 自然语言控制 | 完整实现：大模型解析 `{房间, 设备, 动作, 参数}` 四元组 + 关键词降级 + 白名单校验 + 危险操作二次确认 |
| E4 | 智能管家 | 完整实现：多轮交流、记住偏好、简化指令与指代、从历史挖掘习惯并主动建议、「为什么这么做」的解释 |

**鼓励做（指导书 1.2）：三项全部纳入范围**

| 项 | 落地方式 |
| --- | --- |
| 提高功能 | 即上方 E1–E4 |
| 三维可视化 | 与平面图共用同一份设计数据，2D 编辑 / 3D 只读渲染两个投影，永远不失配 |
| 多用户与权限 | 家人账号 + 角色（管理员 / 成员）+ 操作留痕 `created_by`；与 2.3 要求的登录同一套实现 |

**允许不做（指导书 1.2 原文是「可以不做」，是许可不是禁止）**

「可以不做」= 允许不完全实现，不是不许做。四项都不当禁区处理：

| 项 | 处置 |
| --- | --- |
| 手机 App / 小程序 / 原生客户端 | **远期适配**：主线是浏览器访问的 Web 系统；桌面形态走已定的 mygo 双形态方案（最小壳 + bindings，第二阶段接入），移动端不投入 |
| 真实硬件对接 | **预留适配层，模拟器先行**：设备层定义 `Adapter` 接口，模拟器只是其中一个实现。Matter / HTTP 等协议将来新增一个实现即可，不动上层。有余力时接一台真实设备（如 Matter 灯泡）作为加分演示 |
| 多租户 | **预留接口，不实现**：不建 `tenant_id` 列（理由见 [`docs/04-架构借鉴清单.md`](04-架构借鉴清单.md) §3.1），但数据访问一律经 `backend/store` 一层、主键用全局唯一 UUID——将来要加租户是「加一列 + 加过滤条件」，不需要改表结构或重建约束 |
| 商业化能力 | 与本项目功能无交集，不做预留 |

**不允许**

- 套用现成商用平台换皮；核心业务逻辑调用第三方成品服务而不自研
- 只写文档不写代码

## 4. 同类产品调研

| 产品 | 形态 | 与本题的关系 |
| --- | --- | --- |
| [Home3D (lohith9/Home_View)](https://github.com/lohith9/Home_View) | 前端纯 2D/3D 户型设计器，React + Canvas + three | 指导书第 4 章的推荐复用对象。**已核验：仓库无许可证**，且 4120 行前端零 TypeScript、无 API 层。结论：只借鉴其「同一份设计数据双投影」的范式，不复制代码 |
| [react-planner](https://github.com/cvdlab/react-planner) | 2D/3D 户型规划，MIT | 许可证干净的可选参考；但 2024-04 后未更新，依赖老旧 |
| [Home Assistant](https://github.com/home-assistant/core) | 开源自动化平台（Apache-2.0），YAML 配置 | **重点参考对象**：其「场景 / 脚本 / 自动化」三分法与 target 寻址直接决定我们 F5 的数据模型。已专门核验，见 [`docs/02-Home-Assistant-参考.md`](02-Home-Assistant-参考.md) |
| 米家 / Apple 家庭 | 商业 App | 交互与场景命名的参照；封闭，不可复用 |

**本组的差异**：上面这些要么只会画图（Home3D/react-planner），要么只会控制（Home Assistant），要么封闭（米家）。本题要求的是**画完图能直接控**，这正是要做的缝合。

Home Assistant 的参考结论（详见 [`02-Home-Assistant-参考.md`](02-Home-Assistant-参考.md)）：借鉴它的**设计契约**（三分法、区域寻址、run mode、单步启用/失败策略、场景快照），不借鉴它的**实现形态**（YAML 优先、Python asyncio、Jinja 模板、Blueprint）。它管不到的部分——按季节与室内外温湿度动态算温、1℃ 滞回、附调节依据——恰好是指导书 F5 的评分区分点，由我们自己实现。

## 5. 技术选型

一句话：**React 19 + TypeScript + three.js 自研前端；Go + PostgreSQL 后端；OpenAPI 契约先行；mygo 桌面壳作为第二阶段的原生形态适配。**

完整理由、被否决的方案、以及第 1 周要跑的 4 项验证见 [`docs/adr/0001-技术栈选型.md`](adr/0001-技术栈选型.md)。指导书 3.3 要求「可替换但需在设计文档说明理由」，该 ADR 就是那份理由。

## 6. 分工表

> **3 人组**，设组长 1 名。按「三条纵切轨」分工，每条轨从上到下贯穿五层，避免按层切导致的互相等待。三条轨的边界由 OpenAPI 契约界定，A 轨是唯一的契约修改入口。

| 轨 | 成员 | 职责 | 主要交付 | 起步顺序 |
| --- | --- | --- | --- | --- |
| **A 数据与契约**<br>（组长） | 待填 | 表结构与迁移、OpenAPI 契约、F1 物品管理（CRUD / 搜索 / 筛选 / 导入导出）、seed 数据、多用户与权限（账号 / 角色 / `created_by`）、E3 后端（四元组解析 + 关键词降级 + 白名单）、E4 解释文案 | `sql/` 迁移、`backend/store/`、`backend/api/`、`openapi.yaml`、`scripts/reset.sh` | **第一批**：表结构 + `openapi.yaml`（含 Cookie 认证）+ 鉴权中间件与 2–4 个家人账号；随后 F1、E3、E4 解释 |
| **B 前端与建模** | 待填 | 前端脚手架、F2 类型模板驱动的动态表单、F3 平面图、三维视口、F5 步骤编辑器界面、E3 输入与二次确认界面、E4 对话界面、主题层与看板娘 | 「新增类型不改前端」的实证、可建图、2D/3D 双投影、可编辑场景 | 契约就绪后起脚手架与平面图；其后动态表单、三维视口、场景编辑器、主题层 |
| **C 运行时与策略** | 待填 | 设备模拟器、F4 命令 / 状态 / 历史 / WS 推送、F5 执行引擎、E1 环境自适应、E2 栅格 A* 与轨迹、E4 偏好与习惯挖掘 | 三处一致、场景可执行、设备可移动 | 模拟器接口就绪后接 F4 链路；其后执行引擎、E1、E2、E4 |

组长兼任 A 轨，是因为契约是三条轨唯一共享的东西——谁改契约谁就要对所有下游负责。若组长更擅长前端，可与 B 轨互换，但**契约守门人必须是同一个人**，不能两人共管。

**范围不设弃项**：F1–F5、E1–E4、三维可视化、多用户与权限全部在范围内。表中的周次是**指导书的建议节奏**，不是承诺；实际推进以依赖顺序为主（契约 → 数据 → 一条端到端链路 → 各功能并行展开）。需要调整范围时由全组决定并记进 Issue，不由任何人单方面裁掉。

### 协作方式

采用**迭代增量交付**：三个迭代，每个迭代末产出可运行版本并附测试报告；任务用 GitHub Issues 看板管理；每周一次集成与代码互评。

| 节奏 | 动作 | 对应要求 |
| --- | --- | --- |
| 周一 15 分钟 | 站会：上周合了什么、本周合什么、卡在哪（写进 Issue 评论，不单独留纪要） | — |
| 周四 | 集成日：全员合入 `main`，跑通 `start.sh` | 指导书 5.3「每周至少一次完整合并与联调」 |
| 周五 | 每人 review 他人至少一个 PR，记录落 `docs/reviews/` | 指导书 1.3「至少每周一次代码互评，记录计入过程考核」 |
| 迭代末 | 打 tag `v0.1` / `v0.2` / `v0.3`，附测试报告 | 指导书进度表「可交付版本」 |

**尽早先出 walking skeleton**（第 9–10 周就可以动手，不必等第 12 周）：由 A 轨一人搭出一条端到端链路（一张表 + `GET /api/items` + `POST /api/items/{id}/commands` + 一条 `/ws/state` 推送 + 一个开关按钮 + 一个改内存的模拟器），合入 `main` 后全组从它开分支。它不是 MVP——只求「通了」，不求「能用」；范围限定为这一条链路，不往里加功能。

指导书 1.3 要求：**不得有只写文档不写代码的成员**；故上表三人均有代码产出，评审记录落 `docs/reviews/`。
