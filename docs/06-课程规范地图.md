## 0. 先记住三条总纲

1. **需求说「做什么」，设计说「怎么做」**。把 Redis / Go / React / 五层架构写进需求规格说明书，是课上点名的最常见错误（`第5章 需求分析（第1-2学时）.pptx / slide 11`）。
2. **需求阶段交两套模型，不是一套**：结构化视角（分层 DFD + 数据字典 + 加工说明）与面向对象视角（用例 + ECB 类图 + 顺序图 + 状态图），并且要用矩阵证明两者对得上（`实验三 应用系统需求分析.docx / 任务2、任务3、任务4`）。
3. **设计阶段必须「由图生图」并留下推导痕迹**：DFD → 初始结构图 → 精化结构图；分析类图 → 设计类图；用例 → 设计级顺序图。只交最终图、不写「怎么从上游推出来」，任务 3/4 会按「设计说明完整性」扣分（`实验四 应用系统的软件设计.docx / 3.2、3.5、八`）。

### A2.2 DFD 的层级与顶层图要素

- **顶层图（Context 图）**：全图**只有一个加工**（代表整个系统），四周是外部实体，箭头是进出系统的数据流；作用是定边界、定「与谁交换什么数据」（`第5章 1-2 / slide 24`；`第四讲 / slide 33–35`）。范例见 `大作业/数据流图/顶层图.jpg`（系统画成矩形而非圆形，属 Gane-Sarson 风格）。
  - **编号口径注意**：期中课件把顶层叫「第 0 层」、把第一次分解叫「第 1 层」（`第5章 1-2 / slide 22`）；实验三则叫「顶层图 / 0 层图 / 1 层图」，0 层图 = 第一次分解（`实验三 / 任务2`）。**写文档时统一用实验三口径**（顶层图、0 层图、1 层图），并在图题里写清「0 层（第一次分解）」，避免评委按另一套编号误判层数。
- **0 层图**：把顶层那一个加工拆成 5–9 个主要加工 + 数据存储，覆盖全部主功能（`第5章 1-2 / slide 25`；上限取自 7±2 分解度规则，见 slide 22）。
- **1 层图**：挑 1–2 个核心加工继续拆，子图编号 = 父加工号 + `.序号`（`第5章 1-2 / slide 22`）。实验三要求「至少 3 层」，即顶层/0/1 三档，不是三个子图（`实验三 / 任务2`）。
- **数据守恒**：子图输出必须能从输入推导出来；**局部存储的隐蔽性**：加工内部临时文件不画到父图（`第5章 1-2 / slide 23` 规则⑦⑧）。

### A2.3 数据字典的格式

四类条目（数据流、数据存储、数据项、加工）+ 五个符号（`第5章 1-2 / slide 29`）。表格列可直接照大作业：

- 数据流：数据流名 | 说明 | 来历 | 去向 | 组成（`大作业/模拟期货交易系统.docx / 4.2`）
- 数据存储：存储名 | 说明 | 流入的数据流 | 流出的数据流 | 组成（同上）
- 加工：加工名 | 说明 | 输入 | 输出 | 处理（同上）

### A2.4 用例之间的关系：怎么判、什么时候用

| 关系 | 判定问题 | 适用场景 | 画法 | 典型误用 |
|---|---|---|---|---|
| 关联 | 这个参与者是否启动/参与该用例？ | 参与者与用例之间 | 实线 | 把系统内部对象连到用例 |
| 包含 `«include»` | 多个用例是否有**逐字重复**的步骤，且该步骤**无条件**执行？ | 提取公共功能段（如「身份校验」「日志记录」） | 虚线箭头，**基用例 → 被包含用例**，标 `«include»` | 把可选分支做成 include；箭头画反；被包含用例本身不完整 |
| 扩展 `«extend»` | 该行为是否**只在特定条件**发生，且原用例没有它仍然完整？ | 可选/异常分支（如「忘记密码」「使用优惠券」） | 虚线箭头，**扩展用例 → 基用例**，标 `«extend»` 与扩展点 | 用 extend 表达公共段；扩展用例反客为主 |
| 泛化 | 子用例是否是父用例的一种**特化**、可替换父用例？ | 支付方式、登录方式等同一目的的不同实现 | 实线 + 空心三角，**子 → 父** | 目的完全不同的两个用例做泛化 |

- 四种关系的定义与图例：`第三讲 需求.pptx / slide 23–24`。
- 判定口诀与对照表：`补充-用例图.pptx / slide 25–29`（「重复→包含；正常行为的变化→扩展；包含无条件、扩展按条件；扩展用例不是共用用例」）。
- 一句话记法（推测）：**能共用且必做 → include；可选用且有时才做 → extend；是同一件事的不同做法 → 泛化**。

## A3. 非功能需求的分类与量化写法

### A3.1 分类：用「八大综合要求」，不要自创维度

功能、性能、可靠性与可用性、出错处理、接口、约束、逆向需求、将来可能提出的要求（`第5章 需求分析（第1-2学时）.pptx / slide 6`）。其中「逆向需求」（系统**不应**做什么）与「将来可能」最容易被漏，课上专门列了例（`同上`）。

与指导书 2.3 的六维对照：性能、可靠性、可用性、安全性、可扩展与可维护、兼容性（`指导书 / §2.3`）。**写作时以八大类为章，把指导书六维映射进去**；安全性在八大类里没有独立条目，落到「约束」+「逆向需求」最自然（`第5章 1-2 / slide 6、11`，此映射为推测）。

### A3.2 量化模板：一句话必须能被测试

> **在〈条件〉下，〈指标〉达到〈阈值〉，用〈度量方法〉验证。**

- 反例：「响应要快」；正例：「90% 的请求 ≤ 2 秒」（`第5章 1-2 / slide 9`）。
- 反例：「支持高并发」；正例：「3000 并发下错误率 ≤ 0.1%」（`第5章 3-4 / slide 28`）。
- 设计阶段的质量属性场景按四要素写：**刺激—环境—响应—度量**（`实验四 / 任务1、3.4`）。实验四 T1 原文即「按『刺激—环境—响应—度量』写出不少于 3 条质量属性场景」。学生报告里扩成六要素「刺激源—刺激—环境—制品—响应—响应度量」（`实验4/实验四_实验报告_应用系统的软件设计.md / 任务1`，学生实践），可作细化模板，但**评分只认四要素齐全 + 可度量**。需求阶段可以先用「指标+阈值+验证方法」的简表，到设计阶段再升级为 QAS。

| 编号 | 八大类 | 需求陈述 | 量化指标（条件+阈值） | 验证方法 | 关联需求 | 优先级 |
|---|---|---|---|---|---|---|
| NFR-01 | 性能 | 平面图操作流畅 | 50 件家具内 ≥30 FPS（1366×768，Chrome） | 帧率采样 | F3 | Must |
| NFR-02 | 性能 | 控制指令及时 | 端到端 ≤1s（局域网，P95） | 打点日志 | F4 | Must |

## B2. 系统结构图 / 层次图怎么画，模块划分讲什么

### B2.1 从 DFD 到结构图的固定动作

1. 复查并精化 0 层 DFD；
2. 判定流特性：整体是变换型还是事务型；**一张图里两类并存时，按加工分区判断**，不要对整张 0 层图下结论（`实验四 / 3.2`）；
3. 划输入/输出边界，孤立变换中心；
4. 第一级分解：顶层主控 `Cm` + 传入控制 `Ca` + 变换控制 `Ct` + 传出控制 `Ce`；**事务型分支另画「事务中心 → 动作路径」**，指导书并未给事务中心规定代号（`实验四 / 3.2`；`第五讲 / slide 23–25`）。部分学生用 `M-Tx` 表示事务控制模块，属自建约定，不是课程原文（`实验4/CONTEXT.md`，学生实践）。
5. 第二级分解：把每个控制模块下的具体加工映射成模块；
6. 启发式精化：按 3.5（一）六条改（`实验四 / 3.5`）。

### B2.2 图上必须有的元素

- 模块矩形、调用箭头、模块编号（`M-Cm`、`M-Ca-01`…）、模块名用「动词+名词」而不是序号（`实验四 / 任务3`）。
- 调用箭头旁标主要数据流/控制流（实验四 T3 明文要求「标注调用关系与主要数据」）。
- 图号图题，正文引用一致（`实验四 / 七`）。

> 大作业的 `系统结构图.jpg` 是**纯树形层次图**：竖排模块框、只有调用线、没有编号/数据流标注。那是 2023 年的旧式画法，**形态可参考，内容不能照抄**——2026 实验四要求编号、数据/控制流、精化对照三样齐全（`大作业/系统结构图/系统结构图.jpg`；`实验四 / 任务3、七`）。

### B2.3 内聚/耦合等级表要不要写进文档

- 课件给了完整等级表：内聚 7 级（偶然→逻辑→时间→过程→通信→功能→信息）、耦合 6 级（内容→公共→控制→标记→数据→非直接），并明确「尽可能高内聚、低耦合」（`第五讲 / slide 13–16，表6-1、6-2`）。
- **评分并不要求抄全表**；要求的是「以度量说明模块独立性」并做优化（`实验四 / 3.1、3.5`）。建议在模块清单里加两列「内聚类型 / 耦合类型」，只对 ≥5 个关键模块各写一句理由，比重抄两张表更省篇幅、也更能得分（推测，依据是 3.5 的「逐项写调整前后对照与依据」）。

### B2.4 模块说明（IPO）四要素

模块名称与编号 + 所属上层模块；输入/输出信息（名称、类型、来源与去向、控制信息、返回状态）；模块内部数据与过程陈述（局部数据结构、主要步骤、判定点、循环、异常）；约束与特殊说明（`实验四 / 附录 B`）。≥5 个关键模块（`实验四 / 任务3`）。

### B3.1 BCE / 鲁棒性分析的三条合法性规则

课堂练习「借阅图书」的讲评投影给了标准答案与三类高频错误（`练习/练习2讲评：答案与常见错误_1.JPG`）：

1. **参与者（Actor）不是系统内部类，不能画成边界类**。Actor 在系统边界之外，只能与边界类关联。→ 反例：「把『读者』画成边界类」。
2. **实体类只能与控制器交互，不能直连界面/边界类**。→ 反例：「让『借阅记录』直连界面」。
3. **实体是「可持久化的业务事实」，不是界面，也不是设备/实现细节**。→ 反例：「把打印机、数据库当实体」。

补充两条（`练习/BCE-02-借阅图书BCE类图-圈出违反健壮性规则之处.png`，学生整理，标「推测为课堂补充」）：

4. **边界类之间不直接通信**，必须经控制类转发。
5. **一个用例通常只有一个控制类**；资格校验这类小逻辑并入控制类，不单独立类（讲评原文：「借阅控制（1 个），资格校验可并入其中」）。

三类类的职责定义：边界负责外部交互、控制协调流程、实体保存数据（`第5章 3-4 / slide 11`）；分析类图常用「上边界、中控制、下实体」的三行布局（`第5章 3-4 / slide 12`）。

### B3.2 设计类图与分析类图的差别

分析类图回答「有哪些对象」，设计类图回答「以何种职责、接口与关系协作」；设计阶段要补齐属性类型、方法签名与可见性，明确多重性，拆分控制类职责，为外部服务定义独立接口（`实验四 / 3.3`）。第五讲给的类表格式是「类名 | 属性 | 基本方法 | 方法说明」，属性带 `-`、方法带 `+`、类型后缀 `:String`（`第五讲 / slide 44–56，表6-15、6-16`）；**图与表二选一不够，实验四要图，表可作为附录**（推测）。

## C2. 高频错误清单（按图种）

### C2.1 DFD

课上给的 11 条规则「既是画图规范，也是考试与工程评审的评分点」（`第5章 1-2 / slide 23`）。学生作业六处错误：加工无输入、加工无输出、外部实体之间直接流动、外部实体直连数据存储、数据流命名空洞、加工缺编号（`第5章 1-2 / slide 28`）。纠错口诀：**加工必进出、数据必经加工、存储只连加工、命名要具体、编号要分层**（同上）。

### C2.2 用例图 / 用例关系

- 把 Actor 画成系统内部类、把实体直连界面、把设备/数据库当实体（`练习/练习2讲评…JPG`）。

### C2.3 类图

- 分析阶段：只有实体类，没有边界/控制；关系只有关联，没有组合/继承（`实验三 / 任务3`）。
- 设计阶段：属性无类型、方法无签名、无可见性、无多重性（`实验四 / 任务4`）。
- 把「数据库」「打印机」「界面控件」当实体（`练习/练习2讲评…JPG`）。

- 状态图多个初态；把另一个对象的状态混进来；转换只写事件、不写守卫/动作（`第5章 3-4 / slide 17、20`）。
