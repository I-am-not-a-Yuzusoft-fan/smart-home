# docs 目录导航

新人（尤其是 Windows 队友）先看 [onboarding.md](onboarding.md)：环境怎么装、项目怎么跑、任务怎么合进来。

本目录区分两类文档，**不要混用**：

- **`deliverables/` —— 交付物**。按课程设计指导书 1.4「最终需要提交的成果」编号，是要交给老师的东西。
- **`notes/` —— 过程笔记**。调研、选型、验证、课程规范整理。它们不是交付物，但会是交付物的素材来源，也是"为什么这么做"的证据。

区分的原因很简单：交付物要能独立阅读，不能出现"详见某次讨论"；过程笔记要保留推演与试错，不必写得像正式文档。早期把两者混在 `docs/00-…` 到 `docs/08-…` 里，编号顺序与实际交付清单对不上，容易漏交（可行性报告就是这么漏掉的）。

## 4 图表

- 源码：`diagrams/src/`（PlantUML `.puml` 与 Graphviz `.dot`）
- 产物：`diagrams/svg/`（20 张：顶层与分层 DFD、用例图、领域模型类图、两张状态图、ER 图、分析/设计级顺序图、ECB 类图、单一写入点、分层架构、部署图、初始/精化结构图、实体/服务设计类图、页面结构图、前端组件层级图）
- 重建：`../scripts/build-diagrams.sh`（需要 `plantuml` 与 `dot`，本机实测 plantuml 1.2026.10 / graphviz 16.1.1）

**只提交 SVG，不提交 PNG 或截图。** 课程明确「手绘拍照或整页截图作唯一图件不计分」，而 SVG 里每个字都是真 `<text>` 元素，可检索、可缩放、可 diff。

## 5 命名与编号约定

- 交付物文件名 = `<指导书编号>-<名称>.md`，编号必须与 1.4 一致，不允许重排（课程明确「编号规则中途变更扣分」）。
- 过程笔记文件名 = `<两位序号>-<名称>.md`，序号只表示阅读顺序，**与交付物编号无关**。
- 需求编号 `FR-x.y`：x=1–5 对应 F1–F5，x=6–9 对应 E1–E4；非功能需求 `NFR-n`。
- 图表编号 `图 n`，与附录中的图题一致，正文引用必须能对上。

## 6 写作原则（来自课程要求，不是个人偏好）

1. **需求说"做什么"，设计说"怎么做"。** 需求规格说明书里不出现技术栈名词——这是课件点名的最常见错误。
2. **必含是下限不是上限。** 指导书写"必含"的六项必须做，"鼓励做"的三项也要做，其余能做的尽量做（用户原话：「应做尽做」）。
3. **由图生图，留推导痕迹。** 设计阶段要能从 DFD 推出结构图、从分析类图推出设计类图，只交最终图会被判"设计说明不完整"。
4. **图内文字必须可检索，图有编号有标题。**
5. **可行性报告按课程的五个维度写，不按指导书备注的四项写。** 技术 / 经济 / 操作 / 法律 / 社会，一票否决；经济维度必须给出投资回收期、NPV、ROI 与假设条件。
6. **图表一律用代码生成，不在 Markdown 里画。** PlantUML / Graphviz 源码放 `docs/diagrams/src/`，产物 SVG 放 `docs/diagrams/svg/`，改完跑 `scripts/build-diagrams.sh` 并转 PNG 目视核对。禁止用代码块或 ASCII 字符拼图——图内文字必须可检索（课程实验四明文扣分项），而且 ASCII 图在网页上会散架。
