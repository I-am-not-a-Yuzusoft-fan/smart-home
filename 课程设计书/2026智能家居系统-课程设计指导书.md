# 一、课程设计概述

## 1.1 背景与目标

智能家居以住宅为载体，依托物联网技术将照明、传感、家电等各类终端接入统一平台。系统需要对房间、墙体、家具等家居要素进行空间建模，统一管理所有智能设备的运行状态，支持用户和设备之间的实时交互，按照预设规则实现场景联动控制，并通过可视化界面展示环境信息与设备状态。智能家居属于典型的分布式软件系统，涉及异构设备接入、并发数据处理、事件调度等技术问题。

本课程设计要求每组 3～4 人，在 8 周左右完成一个可运行、可演示、架构清晰的智能家居 Web 系统，走通“管理家居物品 至 一键场景控制”的完整闭环。

需要达到以下目标：

1. 以智能家居系统为开发载体，掌握复杂软件系统的需求分析、原型设计、编码实现与测试验证方法；运用迭代递增思想，围绕家居空间建模、设备状态管理、实时交互、联动策略、可视化展示等功能进行版本规划与模块分解，逐步搭建智能家居平台，明确各模块接口规范，完成从场景原型到可运行系统的构建。

2. 在智能家居系统开发、文档撰写与成果答辩过程中，客观分析该系统在用户隐私、居家安全、数据存储、设备合规等方面问题；遵循软件工程伦理，重视用户家庭数据保护、访问权限管控，树立安全意识、职业操守，兼顾系统易用性与可持续运维理念。

3. 针对智能家居软件项目开展可行性研判，完成开发工作量、开发周期估算，识别异构设备接入冲突、并发状态同步、网络断线等技术风险；对比不同架构方案、通信方案、存储方案的优劣，完成方案比选，形成合理的项目实施决策。

## 1.2 题目与边界

题目：智能家居系统（Smart Home System）——面向单个家庭，管理其家居物品与智能设备，提供平面图可视化、设备控制、状态查询与一键场景策略能力。

| 类 别 | 说 明 |
| --- | --- |
| 必须做 | 一个 Web 系统（浏览器访问），含前端页面与后端服务；数据需持久化；跑通"建图 — 布家具 — 控制 — 看状态 — 触发场景"主线 |
| 可以不做 | 手机 App / 小程序 / 原生客户端；真实硬件对接（可用设备模拟器替代）；多租户与商业化能力 |
| 鼓励做 | 提高功能、三维可视化、多用户与权限 |
| 不允许 | 套用现成商用平台换皮；核心业务逻辑调用第三方成品服务而不自研 |

# 二、需求要求

需求分析的起点不是功能列表，而是一个具体家庭：先设定户型与面积、常住成员与作息差异、真实痛点（如"下班回家要逐个开灯开空调"，"夏天不知道空调设几度合适"）。角色建议分家庭管理员、普通成员、访客（可选）三类。

## 2.1 必做功能（F1～F5）

五项为必做基线，缺项直接影响功能完成度评分。

| 编号 | 功能 | 要求要点 |
| --- | --- | --- |
| F1 | 家居物品管理 | 全部物品与设备的增删改查；属性含名称、类别、所属房间、坐标、状态；按房间/类别筛选与关键字搜索；支持 JSON 或 CSV 批量导入导出；坐标改动必须落到数据层 |
| F2 | 常用家具库 | 每类家具/设备定义类型模板（名称、默认尺寸、图标、可配置属性）；属性按类型差异化（空调有目标温度/模式/风速，灯有亮度/色温，窗帘有开合度）；每类至少一张示意图；新增类型不需改前端代码 |
| F3 | 平面图绘制与布放 | 绘制墙体（建议网格吸附与端点捕捉）；从家具库拖拽家具并支持移动、旋转、删除；图上选中家具可查看编辑属性；平面图数据必须持久化，刷新后恢复 |
| F4 | 设备控制与状态查询 | 选中设备可下发命令（开关、亮度、温度、模式）；状态在平面图、设备列表、控制面板三处一致；支持当前状态、最近更新时间、历史曲线；命令需有成功/失败/超时反馈；建议用设备模拟器 |
| F5 | 一键控制策略 | 至少实现回家、离家、睡眠 3 个模式；每个模式由"条件 + 动作集"构成，动作可带参数与延时；不能机械设温——必须按季节与室内外温度动态计算目标温度；支持滞回，避免阈值附近反复启停；执行需有过程反馈 |

F5 评分区分点：如果小组直接在代码里写死固定温度，比如固定设为 26℃，只能拿到基础分数。 更好的设计思路，是把 “舒适” 作为调控目标：程序接收季节、室内外温度、湿度这些信息，自动算出合适的目标温度，并且限制在合理区间内 —— 夏季舒适区间 24～28℃，冬季 18～22℃，春秋过渡季节优先建议自然通风；为了避免空调频繁启停，开启和关闭的触发温度设置 1℃的缓冲区间；每次自动调节完成后，还要附带说明调节依据，例如：“当前室温 32℃、湿度 75%，按照夏季温控策略，设定目标温度 26℃”。

## 2.2 选做功能（E1～E4）

按完成度加分，不要求全做。**做深一项优于浅做四项。**

| 编 号 | 功 能 | 要 点 |
| --- | --- | --- |
| E1 | 房间环境感知与自适应 | 接入或模拟温度、湿度、光照、人体存在；低于阈值自动开灯、高湿自动除湿、无人自动关闭；需处理多目标冲突并说明决策规则；支持手动接管（用户操作后自动策略暂时让位） |
| E2 | 可移动设备 | 扫地/移动机器人具备位置、朝向、电量、工作状态；平面图实时显示位置与轨迹；建议实现覆盖路径规划（栅格地图 + A* 或牛耕式），而非随机游走 |
| E3 | 自然语言控制 | 输入"把客厅空调调到 26 度"即可执行；建议大模型意图解析为 {房间, 设备, 动作, 参数} 四元组；必须有降级路径（大模型不可用时退化为关键词匹配）；白名单校验、危险操作二次确认 |
| E4 | 智能管家 | 多轮交流并记住偏好；理解简化指令与指代；从历史操作挖掘习惯并主动建议；需提供"为什么这么做"的解释 |

| 维 度 | 要  求 |

| 安全性 | 登录（单用户口令或简单账号体系即可）；接口参数校验；敏感配置不入库不入仓 |
| 可扩展与可维护 | 新增设备类型不改核心代码；分层清晰、命名规范；有 README 与启动脚本 |

# 三、设计要点

## 3.1 分层架构

**本课程设计强制要求分层架构，这是核心考察点。** 推荐五层，依赖方向必须单向：

| 层  次 | 职 责 | 不该做的事 |
| --- | --- | --- |
| 展示层 | 渲染平面图/3D、采集操作、展示状态 | 不承担 SQL 拼接、业务规则实现 |
| 策略层 | 把"意图"翻译成"设备指令集"；规则求值；环境自适应 | 不关心设备用什么协议、不直接操作数据库 |
| 控制层 | 指令校验、编排、下发、重试、状态回写与广播 | 不写业务规则（"夏天设几度"不属于这层） |
| 设备层 | 设备能力描述、命令执行、状态上报 | 不感知房间与用户 |
| 数据层 | 持久化、查询、事务、缓存 | 不含业务判断 |

依赖流向：**展示层 → 策略层 → 控制层 → 设备层，**数据层被各层以接口方式依赖。禁止反向依赖，也禁止跨层调用。

## 3.2 四条设计原则

- 关注点分离：策略只回答"该做什么"，控制只回答"怎么可靠地做到"，设备只回答"能不能做"。
- 面向接口：层间通过接口通信，便于把模拟器换成真实设备。
- 配置驱动：设备类型、场景策略用配置描述，减少硬编码分支。
- 单一数据源：设备状态以服务端为准，前端只做投影与缓存。

## 3.3 技术选型

技术栈不限，以下为推荐组合，可替换但需在设计文档说明理由。

| 层次 | 推荐方案 | 备选 |
| --- | --- | --- |
| 前端框架 | React 19 + Vite | Vue 3 + Vite |
| 平面图 / 3D | Home3D（React + Three.js） | 自研 Canvas/SVG 2D |
| 后端框架 | FastAPI（Python） | Flask / Spring Boot / Express |
| 数据库 | MySQL 8 / PostgreSQL | SQLite（单机演示可用） |
| 实时通信 | WebSocket | SSE / 轮询（降级） |
| 设备接入 | 自研模拟器 + HTTP | MQTT |
| 部署 | Docker Compose | 本机直接运行 |

最低要求：本机可一键启动（start.sh 或 docker-compose.yml），前端访问 `http://localhost:<port>`；建议前后端分离，后端统一 /api 前缀并由前端代理，避免跨域。

## 3.4 数据模型要点

核心不是表有多少张，而是**设备建模是否有抽象**。建议采用"类型—能力—状态"三层：

- 设备类型：定义一类设备有哪些能力，如空调 = {power, mode, target_temp, fan_speed}。
- 能力：描述单个可读写属性的元数据——键名、数据类型、取值范围、单位、是否可写。
- 设备实例：类型的具体化，持有当前状态与在线状态，绑定到某个家具或房间。
- 做到这一层，**新增设备类型只需注册能力描述**，控制层与展示层无需改动（这也是加分项之一）。命令与状态建议统一为带 deviceId、capability、value、requestId 的报文结构；平面图数据（墙体、门窗、家具坐标）建议以 JSON 整体存取。

# 四、基于 Home3D 的开发

Home3D 是开源的家庭平面图编辑器与三维可视化工具，纯浏览器运行，技术栈 React 19 + Vite + Three.js + react-three-fiber + Zustand。核心价值是**同一份设计数据、2D 与 3D 两个投影，天然同步不失配。**

仓库：https://github.com/lohith9/Home_View（核心代码在 frontend/ 目录）。

## 4.1 可直接复用的能力

2D 平面图编辑（网格吸附、吸附引导线、墙体绘制、家具拖放）；约束引擎（门窗自动贴墙、端点与角点吸附）；碰撞引擎（AABB 重叠检测与推出）；参数化依赖（移动墙体，其上门窗随之移动）；实时 3D 视口；撤销/重做；本地存储。

## 4.2 获取与运行

```
git clone https://github.com/lohith9/Home_View.git
cd Home_View/frontend
npm install
npm run dev        # 默认 http://localhost:5173
```

要求 Node 18 及以上；端口被占用可用 npm run dev -- --port 5174。

## 4.3 三种集成路线

走 B 路线的关键改点：在 store 的持久化出口挂适配器，把设计对象同步到后端；给家具对象增加设备标识，建立"图元 ↔ 设备"关联；在 3D 中按设备状态渲染效果（灯用自发光、窗帘按开合度改几何）；新增"设备图层"叠加实时状态。

| 路线 | 做   法 |
| --- | --- |
| A. iframe 嵌入 | 把 Home3D 作为独立页面嵌入，用 postMessage 通信 |
| B. Fork 改造（推荐） | 克隆源码到本组工程，改造其 store 与后端对接 |
| C. 复用引擎 | 只用其 src/engine/ 纯函数与数据结构，自建 UI |

## 4.4 四个常见问题

- **单位与坐标：**先摸清其内部单位与坐标系，再与后端对齐，否则"图上一米、库里十米"。
- **性能：**家具多时避免在 useFrame 里做重计算，用 useMemo 与实例化渲染。
- **模型导入：**目前只支持内置家具目录，自定义 3D 模型需自行扩展渲染组件（加载 glTF）。
- **许可与署名**：使用开源代码须遵守其许可证并在文档与致谢中注明来源，不得改个标题当作原创交付。

- **第 13 周 功能演示：**至少跑通"建图 → 布家具 → 控制 → 看状态"。
- **第 15 周 代码冻结：**之后只修缺陷，不加功能。
- **第 16 周 验收:**交付全套材料，现场演示、答辩

## 5.3 Git 规范

主分支 main 保持可运行，功能在 feature/<模块> 分支开发，合并前需他人评审；提交信息用 feat/fix/docs/refactor/test 前缀；禁止向 main 强推，禁止提交密钥、数据库密码与 node_modules；每周至少一次完整合并与联调。

## 6.1 评分维度

| 维  度 | 考察内容 |
| --- | --- |
| 需求设计合理性 | 场景真实、需求完整、优先级清晰、建模规范 |
| 软件架构合理性 | 分层清晰、职责单一、依赖正确、抽象到位、可扩展 |
| 功能完成度 | 基础功能完整可用，提高功能有深度 |
| 展示效果 | 界面美观、交互顺畅、演示有说服力 |
| 文档与答辩 | 文档规范、表达清楚、问答准确 |

## 6.2 分档标准

| 等 级 | 分  数 | 判定标准 |
| --- | --- | --- |
| 优秀 | 90～100 | 五项必做功能全部完成且体验良好；架构分层严格、抽象合理；至少两项选做功能有实质深度；演示流畅有亮点；文档规范、答辩清晰 |
| 良好 | 80～89 | 必做功能完整；架构基本合理但有少量越层或耦合；一项选做功能较完整；演示顺畅；文档齐全 |
| 中等 | 70～79 | 必做功能基本完成但有明显缺陷；分层流于形式（策略与控制混在一起）；提高功能仅浅尝 |
| 及格 | 60～69 | 必做功能缺项或部分不可用；架构混乱；无提高功能；文档单薄 |
| 不及格 | <60 | 必做功能不可运行；抄袭或无法说明代码；无有效文档 |

## 6.3 答辩

10 分钟汇报（需求 → 架构 → 演示 → 难点与取舍 → 不足与改进），5 分钟问答。重点问架构决策理由、边界情况（"传感器离线怎么办？"）、扩展性（"加一个新设备类型要改哪些代码？"）。

**现场需能即兴修改一处配置并生效**（新增一个场景、调整一个阈值），验证系统不是"演示专用硬编码"。
